ATProto Record

one piece of data — a post, a like, a follow, a profile

by Charles Iliya Krempeaux

In the AT-Protocol (ATProto), a user's data is made of records. Each post is a record. So is each like, each follow, each block, and the user's profile.

A record is a JSON-like object, with a $type field that says what kind of record it is. For example, a Bluesky post:

Notice what is not in the record — no author, no id, no address. A record does not need them. Who wrote it is the repository it is stored in. Its name is its collection and record key. And, its fingerprint is its CID — a hash of its contents.

Where Records Live

Every account has a repository, hosted on its Personal Data Server (PDS). The repository specification says:

Each atproto account has a repository (or "repo") which stores all of their public data records. Repository contents are entirely public and verifiable ("self-certifying").

And:

At a high level, a repository is a key/value mapping where the keys are path names (as strings) and the values are records (CBOR objects).

Each path has 2 parts — a collection and a record key:

collection

the record type — an NSID, such as app.bsky.feed.post. All records of the same type are in the same collection.

record key (rkey)

the name of one record within that collection — such as 3n2opitxdyc2j, or self.

A repository is meant to hold “up to single-digit millions records”, according to the specification.

Naming a Record

A record is named by an at:// URI — the repository's DID, then the collection, then the record key:

Note that a record key is only unique within a collection. The specification says: “The tuple of (did, rkey) is not unique; the tuple (did, collection, rkey) is unique.”

Record Keys

Each record type's lexicon says what kind of record key it uses (its key field). There are 4 kinds:

tid

a timestamp identifier, such as 3n2opitxdyc2j. The most common kind — used for posts, likes, follows, etc. It is usually made from the current time, so records of the same type sort roughly by creation time.

literal:<value>

one fixed record key — so there is only ever one record in the collection. The common one is literal:self — for example, a Bluesky profile is always app.bsky.actor.profile/self.

nsid

the record key must be an NSID. (For example, published lexicons use the NSID as the record key.)

any

any valid record key — for example, a domain name, or a number. This lets the record key mean something, so a record can be looked up by a known name.

Whatever the kind, a record key must be 1 to 512 characters, using only letters, digits, and . - _ : ~. It cannot be . or ... And, it is case-sensitive.

One warning, from the specification: “Record keys are "user-controlled data" and may be arbitrarily selected by hostile accounts.” So, do not trust a tid record key as the record's real creation time.

The Data Model

Records (and all other ATProto data) follow the data model. It can be written 2 ways:

JSON

for HTTP APIs — easy to read.

CBOR (specifically, DRISL)

for storing, signing, and hashing — the exact bytes are always the same for the same data.

The specification says:

When data needs to be authenticated (signed), referenced (linked by content hash), or stored efficiently, it is encoded in Concise Binary Object Representation (CBOR). […] The specific normalized subset of CBOR used in the atproto data model is called DRISL (which is successor to DAG-CBOR).

A few rules worth knowing:

  • No floating-point numbers. The specification explains that de-serializing and re-encoding floats “is not always consistent” — and with content hashes, the bytes must be exactly the same every time. If you need a fraction, use a string (or an integer, such as cents instead of dollars).
  • Field names starting with $ are reserved for the protocol ($type, $link, $bytes). Apps should not make up their own.
  • Missing, null, and “false-y” are all different. Leaving a field out is not the same as setting it to null, which is not the same as setting it to false, 0, or an empty array.

Blobs

Images, videos, and other files are not put in records. They are uploaded separately (as BLOBs), and the record refers to them:

ref is the hash (CID) of the file, mimeType is its type, and size is its length in bytes. Since every blob reference has "$type": "blob", software can find them without knowing the record's lexicon. (To download one, use com.atproto.sync.getBlob on the account's PDS. See: How-To Backup an ATProto PDS.)

(Some old records use a legacy format, with just cid and mimeType. Software should accept it, but never write it.)

CIDs: A Record's Fingerprint

Every record has a CID (Content IDentifier) — a hash of the record's DRISL-CBOR bytes. For records, the specification's “blessed” format is:

  • CID version 1,
  • codec DRISL (0x71, also known as dag-cbor) — or raw (0x55) for BLOBs,
  • hash SHA-256, and
  • written as a string in base32 (starting with b) — which is why record CIDs start with bafyrei, and blob CIDs with bafkrei.

Since the CID is computed from the contents, anyone can check that a copy of a record is genuine — no matter where they got it. The specification calls this “self-certifying”:

Hash references do have the property of being "self-certifying", meaning that returned data can be verified against the link hash. This makes it possible to redistribute content and trust copies even if coming from an untrusted party.

And, since changing a record changes its CID, a CID names one exact version of a record. That is why references like pinnedPost above (and likes, reposts, and replies) include both the uri (which record) and the cid (which version) — a strong reference (com.atproto.repo.strongRef).

Reading and Writing Records

Records are read and written through the account's PDS:

When a record is written, the PDS may check it against its lexicon (by default, only if it knows the lexicon). Then, it makes a new signed commit to the repository, and announces the change on its firehose — which is how relays and AppViews find out.

Deleting Records

A deleted record is really gone from the repository. The repository specification says: “Record deletion is supported without leaving a trace or "tombstone" of previous contents.”

And, other services should remove it too. The accounts specification says: “When accounts remove records from their public repositories, hosting services should remove public access to that content.”

Records in Spaces

Everything above is about public records. The proposal for spaces adds permissioned records — stored in a separate space repo (one per user, per space), with a longer at:// URI that includes the space. (That is a proposal, and not yet part of the specification.)

Summary

An ATProto record:

  1. is one piece of data — a post, a like, a follow, a profile, etc,
  2. is stored in an account's repository, at a path made of a collection (NSID) and a record key,
  3. is named by an at:// URI — DID, collection, record key,
  4. always has a $type, and its shape is set by its lexicon,
  5. follows the data model — JSON or DRISL-CBOR, with no floats, and blobs stored separately, and
  6. has a CID — a hash of its contents, which anyone can check.
