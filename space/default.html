AT-Protocol (ATProto) Spaces

permissioned data in ATProto

by Charles Iliya Krempeaux

Most data in the AT-Protocol (ATProto) is public. Posts, likes, follows, profiles — anyone can read them.

Spaces are a proposed addition to ATProto for data that is not public — data that only some people (and some applications) are allowed to read. The proposal calls this permissioned data, and gives these examples:

  • Personal data: bookmarks, mutes, drafts
  • Gated content: paid newsletters, subscriber-only posts
  • Socially shared: private posts, stories
  • Groups: private forums, communities, group chats

A space is not a server, and it is not a place where the data is kept. A space is a boundary — a group of records, and a rule about who may read them. Each user's records stay on that user's own PDS.

The proposal says:

A space is an authorization and sync boundary representing a shared social context. A space may include many different types of records from many users. The space does not colocate records on a single network host.

Note! At the time of writing, spaces are a proposal — proposal 0016, “Atproto Spaces”. They are not (yet) part of the ATProto specification. The proposal itself says:

This is a proposal, not the final specification. Details, terminology, and behaviors are all likely to change.

There are also draft lexicons, and a work-in-progress implementation, in bluesky-social/atproto pull request #5187 (open, not merged, at the time of writing). This article describes the proposal as of November 2026.

Public Data versus Space Data

Spaces are shaped a lot like public ATProto data. Users still have their own repositories, records still have lexicon types, and applications still pull data from PDSes to build their views. But, many of the details are different. The proposal compares them like this:

And, there are no relays and no firehose for spaces. Applications pull space data directly from each user's PDS.

The proposal sums up the difference this way:

Public broadcast is built for open distribution (signed, archival, rebroadcastable) while atproto spaces are built for party-to-party transmission within an access boundary.

Access Control, Not Secrecy

Spaces control who may read the data. They do not encrypt it. The servers that handle the data (PDSes, and the applications that are allowed in) can read it. The proposal says:

Atproto spaces provide access control, not confidentiality. They are not end-to-end encrypted.

That is on purpose — it is what lets applications offer search, notifications, moderation, etc, on space data. End-to-end encryption could be added on top, by an application, but it is not part of the proposal.

Naming a Space

A space is identified by 3 things:

space authority

a DID — the root of authority for the space, which decides who may read it. It might be a user's own DID (for example, for their bookmarks), or a DID made just for the space (for example, for a forum).

space type

an NSID naming what kind of space it is — for example, com.atmoboards.forum. It resolves to a space type declaration (a lexicon with "type": "space"), which lists the record collections to expect. It is also what a user consents to, in OAuth — for example, “access to your AtmoBoards forums”.

space key (skey)

a string that tells apart spaces of the same type, under the same space authority — like a record key. For example, general.

Who Is Involved

The proposal describes these roles:

repo host

stores and serves users' space repos (one user's records in one space). Usually, the user's own PDS.

space host

answers for a space as a whole — it decides who may read (by issuing space credentials), keeps track of who has written (the writer set), and sends out notifications. It never stores the records themselves. Usually, the space authority's PDS.

syncer

an application that keeps its own copy of a space, by pulling from the repo hosts — for example, an AppView for a private forum.

managing app

an outside service that a space host can ask “may this account read, and may it write?” — for spaces whose rules are not a simple member list (for example, “paying subscribers only”).

Notice that a PDS usually plays 2 of these roles — repo host for its accounts, and space host for the spaces its accounts are the authority of.

(There is also the space mirror — but that is not from the proposal. It is a way of building an application: one internal syncer that serves its copy to the application's other services.)

How Reading a Space Works

In short:

  1. A user authorizes an application, with an OAuth space: scope.
  2. The application gets a delegation token from the user's PDS (proof that the user authorized it).
  3. The application gives that (and, maybe, a client attestation — proof of which application it is) to the space host, and asks for a space credential.
  4. If the space's rules allow it, the space host returns a short-lived space credential (10 minutes, by default).
  5. The application asks the space host who has written to the space, then pulls each user's space repo from its repo host, using the space credential.
  6. The application keeps its copy up-to-date, as the space host notifies it of changes.

(For the details, see: ATProto Syncer.)

Who May Read: Policies

The core protocol does not say how a space host decides who may read, or whose writes count. Each space has a policy for that. Every PDS must support these 3:

com.atproto.personalspace.policy

only the space authority's own account has access — for bookmarks, mutes, drafts, etc.

com.atproto.memberspace.policy

access is checked against a member list kept by the PDS.

com.atproto.managedspace.policy

access is decided by an outside managing app.

(For more, see: ATProto Space Host.)
