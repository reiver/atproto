ATProto Spaces XRPC API End-Points

every com.atproto.space end-point, who implements it, and who calls it

by Charles Iliya Krempeaux

Spaces are a proposed addition to the AT-Protocol (ATProto) for permissioned data — records that only some people (and some applications) are allowed to read. For example: a private forum, a paid newsletter, or a user's bookmarks.

All of the XRPC API end-points for spaces live in one namespace. The proposal says:

All protocol XRPC methods for atproto spaces are currently defined under the com.atproto.space namespace.

There are 28 of them. This article lists them all.

The proposal groups them into 4 roles — space host, repo host, PDS, and syncer. But, a role is a kind of end-point, not a separate server. Usually, a single PDS implements the space host, repo host, and PDS end-points (26 of the 28). The other 2 — the syncer end-points — are implemented by applications. The proposal says:

This grouping describes kinds of methods, not separate services. A single service (e.g. a PDS) is usually both a repo host for its accounts and a space host for the spaces anchored on it.

Note! At the time of writing, spaces are a proposal — proposal 0016, “Atproto Spaces”. They are not (yet) part of the ATProto specification. The proposal itself says:

This is a proposal, not the final specification. Details, terminology, and behaviors are all likely to change.

Also, there are no published lexicons for these end-points yet. (For example, lexicons/com/atproto/space/authorizeSpaceSync.json does not exist in the bluesky-social/atproto repository, at the time of writing.) So, this article gives each end-point's name, role, type, auth, and purpose — as the proposal describes them — but not every parameter.

This article describes the proposal as of November 2026.

XRPC, Briefly

An XRPC end-point is named by an NSID, and is called over HTTP at /xrpc/ followed by that NSID. For example:

Each end-point is one of 2 types:

query

an HTTP GET, with the inputs in the query string. It reads; it does not change anything.

procedure

an HTTP POST, usually with a JSON body. It does something.

In the tables below, end-points are written without the com.atproto.space. prefix. So, listWriters means com.atproto.space.listWriters.

The 4 Kinds of Auth

The space end-points use 4 kinds of authorization:

OAuth

an application acting for a logged-in user, with a space: OAuth scope. The scope says which spaces it covers, and what is allowed in them:

  • action — what may be done to records: read_self (only the user's own records), read (everyone's records, and permission to ask for a delegation token), create, update, delete.
  • manage — what may be done to the space itself: create, update, delete.

For example: space:com.atmoboards.forum?authority=*&manage=update&manage=delete.

space credential

a short-lived token, issued by the space authority through authorizeSpaceSync, that lets an application read everything in a space. It is sent with the Atproto-Space-Credential scheme, plus an HTTP Message Signature:

service auth

one server calling another. A short-lived JWT (iss, aud, lxm, exp, …), signed with the calling account's #atproto key.

none (a token in the body)

no Authorization header. Instead, the proof is inside the request body — a delegation token and client attestation (for authorizeSpaceSync), or a notify token (for the syncer end-points).

The read end-points accept either OAuth or a space credential. The write end-points accept only OAuth. The proposal says this is “since a write is attributed to the authoring user”.

Space Host End-Points

A space host answers for a space as a whole — it hands out space credentials, keeps the writer set (who has written to the space), and sends out notifications. It never stores the records themselves. (Usually, it is the space authority's PDS.)

Repo Host End-Points

A repo host stores and serves users' space repos — one user's records in one space. (Usually, it is the user's own PDS.)

A few things to note:

  • The proposal calls listRepoOps the “Primary sync mechanism”. getRepo is for when a syncer starts from nothing (or has fallen too far behind).
  • With OAuth, the read end-points only reach the user's own space repo, on the user's own PDS. To read other users' space repos, an application needs a space credential.
  • When called with a space credential, the end-points that return a commit (getLatestCommit, getRepo, listRepoOps) or a single record (getRecord) require a MAC — the syncer asks for one with an Accept-Signature header, and the repo host returns it in the HTTP headers — so the syncer can check the data really came from the repo host.

Related Names That Are Not on the List

Names in com.atproto.space That Are Not End-Points

The proposal uses 2 other com.atproto.space.* names. Neither is an end-point:

com.atproto.space.defs

shared definitions — for example, com.atproto.space.defs#commit, the commit that summarizes a space repo.

com.atproto.space.policy

a record type (collection). If a space's publishPolicy flag is set, its policy is published as a record of this type (with record key self) in the space authority's own space repo.

Policy End-Points

How a space decides who may read and write is set by its policy. The end-points that belong to a particular policy are not in com.atproto.space. The proposal says: “By convention, these methods live in the same namespace as the policy”.

(The proposal gives checkAccess only as a short name. By the convention above, it would be com.atproto.managedspace.checkAccess.)

What Is Missing

There is no end-point in the list for uploading a BLOB (an image, video, etc) into a space — only getBlob and listBlobs, for reading them. (For public data, ATProto has com.atproto.repo.uploadBlob.) The proposal does not say how a BLOB gets into a space repo.

Summary

  1. All 28 XRPC API end-points for ATProto spaces are in the com.atproto.space namespace.
  2. They are grouped by role — space host (6), repo host (8), PDS (12), and syncer (2).
  3. A role is a kind of end-point, not a separate server — usually one PDS implements 26 of them, and applications implement the 2 syncer end-points.
  4. Read end-points accept OAuth or a space credential; write end-points accept only OAuth; server-to-server end-points use service auth or a token in the body.
  5. Policy end-points (com.atproto.memberspace.*, and checkAccess) live outside com.atproto.space.
  6. There are no published lexicons yet.

Again, this is all a proposal. Details are likely to change.
