ATProto Lexicon

the schema language for records, API end-points, and event streams

by Charles Iliya Krempeaux

Lexicon is how the AT-Protocol (ATProto) describes the shape of its data and APIs. The specification says:

Lexicon is a schema definition language used to describe atproto records, HTTP endpoints (XRPC), and event stream messages. It builds on top of the atproto Data Model.

The schema language is similar to JSON Schema and OpenAPI, but includes some atproto-specific features and semantics.

Each schema is called a lexicon, and is named by a NSID — for example, app.bsky.feed.post (what a Bluesky post looks like), or com.atproto.identity.resolveHandle (an API end-point).

A lexicon is a description, not code — it does not run. It says what fields a record has (and which are required), or what an end-point takes and returns. Software uses it to check data, and to generate code.

And, lexicons are themselves published as ATProto data — as records in a repository (see “Publishing and Finding Lexicons”, below).

A Lexicon File

A lexicon is a JSON document with 4 fields:

lexicon

required — the version of the Lexicon language. Currently always 1.

id

required — the NSID of this lexicon.

description

optional — a short overview.

defs

required — the definitions, by name. The one named main is the primary definition.

Referring to Definitions

A definition other than main is referred to with a # fragment — for example, com.atproto.label.defs#selfLabels. Inside the same file, just the fragment works — for example, #replyRef. The main definition is referred to by the NSID alone.

By convention, definitions used by several lexicons go in a separate *.defs lexicon — for example, com.atproto.label.defs or app.bsky.feed.defs.

A few things worth knowing:

  • knownValues is not a closed list — other values are allowed. enum is a closed list.
  • String lengths come in 2 kinds: minLength/maxLength count UTF-8 bytes, and minGraphemes/maxGraphemes count grapheme clusters (roughly, visible characters — an emoji might be many bytes, but one grapheme).
  • Leaving a field out, setting it to null, and setting it to a “false-y” value (false, 0, an empty array) all mean different things. null is only allowed if the field is listed in nullable.
  • The specification says “Lexicon designers are strongly recommended to not use unknown fields in record objects for now.”

Refs and Unions

A ref means “the definition over there goes here” — it lets a definition be reused. A union means “any one of these definitions goes here”.

Unions are open by default. That means a later version of the lexicon might add more kinds — so software should not reject a kind it does not know about. (A union with "closed": true can never change.)

Since a union could be one of several things, the data has to say which. That is what $type is for.

When to Use $type

Data includes a $type field whenever its type might be ambiguous. The rules are:

  • records must always have $type — since records get passed around outside of repositories, and need to describe themselves,
  • each value in a union must have $type (except at the top level of event-stream messages), and
  • blob values always have "$type": "blob".

And, for a main definition, $type is just the NSID — app.bsky.feed.post, never app.bsky.feed.post#main.

Validation

When an app creates or updates a record, the PDS can check it against its lexicon. The specification describes 3 options:

validation required

the record must be checked. If the PDS cannot find the lexicon, the write fails.

no validation

the record is not checked against any lexicon (though it must still be valid ATProto data).

optimistic validation (the default)

if the PDS knows the lexicon, it checks; if not, the write is allowed. (Also called “fail-open”.)

This is why apps can store new kinds of records in a user's repository, without the PDS knowing anything about them.

Two more rules, for any software that reads the data:

  • Data that fails validation should be treated as entirely invalid — not repaired, and not partly used.
  • But, extra fields (ones the lexicon does not mention) should be ignored — at worst, a warning. Otherwise, older software would break every time a lexicon added a field.

Changing a Lexicon

A lexicon can change over time — but only in compatible ways. The principle is that “all old data must still be valid under the updated Lexicon, and new data must be valid under the old Lexicon.” So:

  • new fields must be optional,
  • types cannot change,
  • fields cannot be renamed,
  • required fields cannot be removed (mark them deprecated instead),
  • closed unions cannot change, and
  • size and length limits cannot be added, removed, or changed.

“If larger breaking changes are necessary, a new Lexicon name must be used.” (You can see this in app.bsky.feed.post above — the old entities field is still there, marked “DEPRECATED: replaced by app.bsky.richtext.facet.”)

When does a lexicon become fixed? The specification says that, at a minimum, once a third party has adopted it. It suggests marking experimental ones in the name — for example, com.corp.experimental.newRecord.

Who Controls a Lexicon

A lexicon is controlled by whoever controls its NSID's domain. The specification says:

The authority for a Lexicon is determined by the NSID, and rooted in DNS control of the domain authority. That authority has ultimate control over the Lexicon definition, and responsibility for maintenance and distribution of Lexicon schema definitions.

So, to make your own record types and end-points, use NSIDs under a domain you control. (See: ATProto NSID.)

Publishing and Finding Lexicons

Lexicons are published as records, of type com.atproto.lexicon.schema, in an ATProto repository. The record key is the NSID. A DNS TXT record says which repository.

Since lexicons are records, changes to them go out on the firehose like any other record. (But, changes to the DNS records do not — so resolvers should not cache them for long.)

Lexicons and Spaces

The proposal for spaces (permissioned data) adds a new kind of lexicon definition — a space type declaration, with "type": "space" — which lists the record collections to expect in a kind of space. That is a proposal, and not part of version 1 of the Lexicon specification.

Summary

An ATProto lexicon:

  1. is a JSON schema, named by an NSID,
  2. describes a record type, an XRPC end-point (query or procedure), an event stream, or a permission set,
  3. describes fields with types like string, integer, object, ref, and union,
  4. is used to validate data — with extra fields ignored,
  5. can only change in compatible ways,
  6. is controlled by whoever controls its NSID's domain, and
  7. is published as a com.atproto.lexicon.schema record, found through a _lexicon DNS record.
