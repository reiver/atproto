ATProto XRPC

how ATProto clients and servers talk to each other over HTTP

by Charles Iliya Krempeaux

XRPC is how the AT-Protocol (ATProto) does HTTP APIs — between apps and servers, and between servers. The specification says:

HTTP APIs for client-server and server-server requests in atproto use a set of common conventions called "Lexicon RPC", or XRPC for short. Endpoint path names include an NSID indicating the Lexicon specifying the request and response schemas, usually with JSON content type.

XRPC is not a separate protocol, and it does not need a special library. It is plain HTTP and JSON, with a few conventions — the path is /xrpc/ plus an NSID, reading is GET, doing is POST, and errors are JSON. Any HTTP client (even curl) can use it.

Queries and Procedures

A lexicon describes an end-point as one of 2 types:

query — HTTP GET

reads something. Inputs go in the URL's query string. Queries “are cacheable and should not mutate resource state.”

procedure — HTTP POST

does something. Inputs usually go in a JSON request body. Procedures “are not cacheable and may mutate state.”

Query Parameters

A few rules for query parameters:

  • Only booleans, integers, strings, and arrays of those, are allowed.
  • An array is sent by repeating the parameter — for example, ?uris=…&uris=….
  • Booleans are sent as true or false.
  • Strings are not quoted.
  • If the lexicon gives a default value, it should be sent anyway — so caching works consistently.

Errors

When something goes wrong, the response should be JSON with 2 fields:

error

required — the name of the error, with no spaces (for example, InvalidRequest).

message

optional — a description, for humans.

Two practical notes:

  • Be ready for errors that are not JSON. The specification says “realistically, many services will return generic load-balancer or reverse-proxy HTML error pages. Clients should be robust to non-JSON error responses.”
  • Use timeouts, limited retries, and randomized exponential backoff — the specification encourages all 3.

Authentication

Some end-points need no login (most reads of public data). Others do (writing, and anything about the logged-in user). The specification admits “there is not yet a consistent way to enumerate which endpoints do or do not.”

There are 4 kinds of authentication:

OAuth

the main way, for apps acting for a user. The specification says: “The primary client/server authentication and authorization scheme for XRPC is OAuth”.

session tokens (legacy)

log in with com.atproto.server.createSession (a handle or email, and a password — ideally an app password), and get back an access token and a refresh token. Send the access token as Authorization: Bearer …. It expires quickly; get a new one with com.atproto.server.refreshSession. Clients should treat the tokens as opaque.

admin (temporary)

for a server's operator — HTTP Basic auth, with the user name admin. Used for com.atproto.admin.*, and a few others.

inter-service tokens

for one service calling another on a user's behalf — a short-lived JWT, signed with the user's signing key.

Service Proxying

Pagination

End-points that return lists usually take a cursor parameter, and return a cursor field. The rules:

  1. leave out cursor on the first request,
  2. if the response has a cursor, send it back (with all the other parameters unchanged) to get the next page, and
  3. stop when a response has no cursor.

Treat the cursor as opaque. (For example, com.atproto.repo.listRecords on a Bluesky PDS happens to return the last record key as its cursor — but do not rely on that.)

Blobs

Files (images, videos, etc) are a special case, since they are not JSON. An app uploads one with com.atproto.repo.uploadBlob — the request body is the raw file, with its Content-Type — and gets back a blob reference to put in a record. Blobs are downloaded with com.atproto.sync.getBlob.

Event Streams

Lexicons can also describe subscriptions — event streams, over WebSockets. They also live under /xrpc/ — for example, the firehose is wss://…/xrpc/com.atproto.sync.subscribeRepos. (See: ATProto Relay.)

Summary

ATProto XRPC:

  1. is plain HTTP and JSON, with conventions,
  2. puts every end-point at /xrpc/ plus an NSID, described by a lexicon,
  3. uses GET for queries (reading) and POST for procedures (doing),
  4. returns errors as {"error": …, "message": …},
  5. authenticates with OAuth (or legacy session tokens), and between services with signed JWTs,
  6. lets the PDS forward requests to other services, with atproto-proxy, and
  7. pages through lists with an opaque cursor.
