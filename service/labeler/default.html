ATProto Labeler

the service that publishes signed labels about accounts and content

by Charles Iliya Krempeaux

A labeler is a type of AT-Protocol (ATProto) service that publishes labels — small, signed statements about an account or a piece of content. For example: “this post is spam”, or “this image is graphic”, or “this account is a bot”.

Labels are how moderation works in ATProto. The ATProto moderation guide says:

Atproto moderation is implemented using Labels.

A labeler does not remove or hide anything by itself. It only publishes labels. It is up to other services (such as an AppView), applications, and users to decide what to do about a label — hide the content, blur it, show a warning, or ignore the label entirely.

And, there can be many labelers. Anyone can run one. Users and applications choose which labelers they want to listen to.

A label is a small data object. The specification says:

The fields are:

ver

the label format version — currently always 1.

src

the source — the DID of the labeler that made the label.

uri

the subject — what the label is about. An at:// URI for a record (such as a post), or a did: for a whole account.

cid

(optional) a particular version of the subject.

val

the value — what the label says, such as spam or porn. At most 128 bytes.

neg

(optional) if true, this label takes back an earlier label. (See “Taking a Label Back”, below.)

cts

when the label was created.

exp

(optional) when the label expires.

sig

the signature. (See “Signatures”, below.)

Notice that a label is not stored in the subject's repository. The person being labeled does not have to agree to it — and cannot remove it. A label is a statement by the labeler, about someone else's content.

Label Values

The specification says very little about what label values mean. It describes them as tokens, similar to hashtags — and recommends lower-case, kebab-case (like-this), using only ASCII letters.

Values that start with an exclamation mark (!) are, by convention, system values — they ask for a particular behavior, rather than describing the content.

The lexicon (com.atproto.label.defs) lists these known values:

!hide

hide the content.

!warn

show a warning.

!no-unauthenticated

do not show to people who are not logged in.

porn, sexual, nudity, graphic-media

adult and graphic content.

bot

an automated account.

And, the specification gives 2 more special values — !takedown and !suspend — which a service can be asked to handle by removing the content entirely. (See “How Labels Reach Users”, below.)

Beyond these, each labeler can define its own values — and describe them in its declaration record (see below).

Taking a Label Back

A label cannot be deleted. Instead, to take one back, the labeler publishes a new label, with the same src, uri, and val — but with neg set to true, and a newer cts. This is called a negation.

(Note that a negation does not mean the opposite is true. It just means the labeler no longer makes that statement.)

A label can also have an expiration time (exp). After that time, services should no longer show it.

Self-Labels

There is one kind of label that does not come from a labeler.

Some record types let the author put labels right inside the record itself — for example, so that someone posting an artistic nude can mark their own post as nudity. These are called self-labels. Their source is the author's own account, and they are proven by the repository's own commit signature, rather than by a separate sig.

A Labeler's Identity

Every labeler is an account, with its own DID. That DID is what appears in the src field of its labels.

a #atproto_labeler service

with the type AtprotoLabeler, saying where the labeler's server is.

Each label value definition says:

identifier

the value itself (lower-case ASCII letters and - only).

severity

inform (neutral, informational), alert (negative, a warning), or none (show nothing).

blurs

content (hide all of it), media (hide just the images, video, and audio), or none.

defaultSetting

what to do by default — ignore, warn, or hide.

adultOnly

whether it is only for adult content.

locales

a human-readable name and description, in one or more languages.

Getting Labels From a Labeler

A labeler offers 2 XRPC API end-points, at its #atproto_labeler serviceEndpoint:

com.atproto.label.subscribeLabels

a WebSocket stream of new labels (and negations). It works like the relay firehose — CBOR frames, with seq numbers and a cursor parameter. Each #labels message has a seq and a list of labels. (Unlike the firehose, the specification says the backfill may go all the way back, with cursor=0.)

com.atproto.label.queryLabels

find the labels for particular subjects. The uriPatterns parameter takes one or more URIs — or prefixes, ending with *.

For example: 


wss://mod.bsky.app/xrpc/com.atproto.label.subscribeLabels

(At the time of writing, mod.bsky.app answered a wildcard queryLabels request with: “Support for wildcard label queries is temporarily disabled”.)

A labeler does not have to make its labels public — or offer these end-points at all.

Signatures

Each label is signed by its labeler. That way, a label can be passed from service to service, and anyone can still check that it really came from the labeler in its src.

To check a label's signature:

  1. take the label, without its sig field (but with its ver field),
  2. encode it as deterministic CBOR (following the DRISL rules),
  3. hash those bytes with SHA-256, and
  4. check the signature of that hash, using the #atproto_label key from the labeler's DID document.

A few rules:

  • If there is no #atproto_label key, do not try other keys. Treat the signature as invalid, and ignore the label.
  • If a signature does not check out, re-resolve the labeler's DID document — its key may have changed.
  • Signatures are meant to be checked when one service receives labels from another. The specification assumes most end-user applications will not check them.

How Labels Reach Users

Most applications do not read labels from labelers directly. Instead, an AppView collects labels from the labelers, and includes the relevant ones in its responses. (The specification calls this hydrating the labels.)

An application says which labelers it wants, with the atproto-accept-labelers HTTP header — a comma-separated list of labeler DIDs:

(That example is from the specification.)

  • The optional ;redact parameter means: for this labeler's !takedown and !suspend labels, remove the content from the response entirely, rather than just labeling it.
  • If the header is left out, the service may use its own default labelers. If the header is present but empty, the service should apply no labels at all.
  • The response's atproto-content-labelers header says which labelers the service was actually able to use.

Then, the application decides what to do with each label — using the labeler's label value definitions (severity, blurs, defaultSetting), and the user's own settings.

Since users can listen to more than one labeler, moderation can be layered — a user might use Bluesky's labeler, plus a community's labeler, plus one that marks spoilers for their favorite TV show. This fits ATProto's idea that speech and reach are separate layers.

Labels and Spaces

Labels, as described above, are for public data.

The proposal for permissioned (private) data — spaces — handles labels differently. A public label about private content would leak information about it. So, in a space, a labeler instead writes its labels as records (of type com.atproto.label.record) inside the same space. And, to read the space at all, a labeler must be let in, like any other syncer.

Running a Labeler

Bluesky's software for running a labeler is Ozone. Its README describes it as a “labeling service for Bluesky and other atproto apps” — with a web interface for reviewing reports, and creating labels, takedowns, and suspensions. It can be self-hosted.

Summary

An ATProto labeler:

  1. publishes labels — signed statements (src, uri, val, …) about accounts and content,
  2. does not hide or remove anything itself — AppViews, applications, and users decide what to do with labels,
  3. is an account, with a #atproto_labeler service and a #atproto_label key in its DID document,
  4. can describe its label values in a declaration record,
  5. offers its labels through subscribeLabels and queryLabels, and
  6. is one of many — users and applications choose which labelers to listen to.
