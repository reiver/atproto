ATProto Feed Generator

the service that decides which posts go in a custom feed

by Charles Iliya Krempeaux

A feed generator is a type of AT-Protocol (ATProto) service that provides a custom feed — its own algorithm for choosing which posts to show, and in what order.

Bluesky's starter kit for building one describes it this way:

Feed Generators are services that provide custom algorithms to users through the AT Protocol.

A feed generator does not return posts. It returns only a list of post URIs — called a skeleton. An AppView then fills in each post's content, author, like counts, etc., before the feed reaches the user.

That keeps a feed generator simple. It only has to decide which posts. It does not have to store or serve the posts themselves.

And, anyone can run a feed generator. The ATProto overview names it as one of the network's supporting services:

There are also supporting services such as feed generators and labelers.

How a Custom Feed Works

When a user opens a custom feed in their application, this is what happens:

  1. the application asks for the feed (app.bsky.feed.getFeed), through the user's PDS, which forwards the request to an AppView,
  2. the AppView looks up which feed generator provides the feed,
  3. the AppView asks the feed generator for a skeleton (app.bsky.feed.getFeedSkeleton),
  4. the feed generator answers with a list of post URIs, and
  5. the AppView fills in (“hydrates”) each post, and returns the full feed.

(The starter kit's README describes an older version of this, where the user's PDS did the hydrating itself. It says: “In the future, the PDS will hydrate the feed with the help of an App View”. Today, as the diagram shows, the hydrating is done by the AppView — for example, asking public.api.bsky.app for a custom feed with getFeed returns fully hydrated posts.)

Two Parts: the Service and the Record

A custom feed has 2 parts:

the service

the feed generator itself — a server, identified by a DID, that runs the algorithm.

the record

an app.bsky.feed.generator record, in the repository of whoever publishes the feed. It gives the feed a name, description, and avatar — and points to the service's DID.

A feed is identified by the at:// URI of its record — not by the service. That means one feed generator service can provide many different feeds.

XRPC API End-Points

A feed generator implements 2 XRPC API end-points:

app.bsky.feed.getFeedSkeleton

This is the main one. It takes these parameters:

feed

(required) the at:// URI of the feed's record — so the feed generator knows which of its feeds is being asked for.

limit

(optional) how many posts — from 1 to 100, and 50 by default.

cursor

(optional) where to continue from, for the next page.

Each item in feed can have:

post

(required) the post's at:// URI.

reason

(optional) why the post is in the feed — either a repost (app.bsky.feed.defs#skeletonReasonRepost, with the repost's URI), or a pinned post (app.bsky.feed.defs#skeletonReasonPin).

feedContext

(optional) a string the feed generator can use for its own purposes. It is passed through to the application, and may be sent back to the feed generator with the user's interactions.

The response can also have:

cursor

for the next page. Its contents are entirely up to the feed generator — it is passed through, unchanged, to and from the application. (The starter kit strongly recommends that it be unique for each feed item — for example, a timestamp plus a CID.)

reqId

a unique identifier for the request, which may be sent back with the user's interactions.

If the feed is not one the feed generator provides, it answers with an UnknownFeed error.

Authentication

The lexicon for getFeedSkeleton says:

Auth is optional, depending on provider requirements, and provides the DID of the requester.

When a logged-in user asks for a feed, the request to the feed generator includes a JWT, signed with the user's key — the same kind of inter-service JWT described in the AppView article:

  • iss is the user's DID,
  • aud is the feed generator's DID, and
  • exp is when it expires.

A feed that is the same for everyone (for example, “all posts about cats”) does not need to check it. But, a personalized feed (for example, “popular posts from people you follow”) needs to know who the user is. The starter kit says:

If you are creating a generic feed that does not differ for different users, you do not need to check auth. But if a user's state (such as follows or likes) is taken into account, we strongly encourage you to validate their auth token.

To validate it, check the JWT's signature against the key in the user's DID document, and check that aud is the feed generator's own DID.

Where the Posts Come From

How a feed generator picks its posts is entirely up to it. At the simplest, it could return a hard-coded list.

But, most feed generators read the relay's firehose, and keep their own index of the posts (and likes, follows, etc.) their algorithm needs. Since they only return post URIs, they can keep as little as they need. The starter kit says:

Since Feed Generators do not need to provide hydrated posts, you can index as much or as little of the firehose as necessary.

The starter kit suggests some ideas:

  • “What's Hot” — keep a running count of likes for each post, and return recent posts with enough likes,
  • a community feed — keep a list of the community's members, and return their posts,
  • a topical feed — filter posts by their text (with a keyword match, or some other classifier).

It also notes that most algorithms do not need to keep posts for long — often, anything older than 48 hours can be thrown away.

Publishing a Feed

To make a feed available to users:

  1. run the feed generator service, on HTTPS (port 443),
  2. make its DID resolvable, with a #bsky_fg service pointing to the server, and
  3. create an app.bsky.feed.generator record in your account's repository, with did set to the service's DID.

After that, users can find the feed, pin it, and share it — the record's at:// URI is how everyone refers to it.

Summary

An ATProto feed generator:

  1. provides one or more custom feeds — each declared by an app.bsky.feed.generator record, and identified by that record's at:// URI,
  2. is a service with its own DID, and a #bsky_fg service in its DID document,
  3. answers getFeedSkeleton with only a list of post URIs — the AppView fills in the posts,
  4. can know who is asking (from the user's JWT), so it can personalize, and
  5. usually builds its own index from a relay's firehose.
