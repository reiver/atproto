ATProto Space Host

the service that answers for a permissioned “space” as a whole

by Charles Iliya Krempeaux

A space host is a type of AT-Protocol (ATProto) service that answers for a space as a whole.

The proposal that defines it puts it this way:

Space Host: a service that answers for a space as a whole, issuing credentials, enumerating writers, and routing notifications.

So, a space host has 3 main jobs:

  1. deciding who may read the space (by issuing space credentials),
  2. keeping track of who has written to the space (the writer set), and
  3. telling syncers when something in the space has changed (notifications).

Note! At the time of writing, spaces and space hosts are a proposal — proposal 0016, “Atproto Spaces”. They are not (yet) part of the ATProto specification. The proposal itself says:

This is a proposal, not the final specification. Details, terminology, and behaviors are all likely to change.

This article describes the proposal as of November 2026.

Spaces, Briefly

A space is a group of records that only some people (and some applications) are allowed to read — for example: a private forum, a paid newsletter, or a user's bookmarks.

A space is identified by 3 things — its space authority (a DID), its space type (an NSID), and its space key (a string):

The records in a space are spread out. Each user stores their own records for a space on their own PDS. (The proposal calls one user's records in one space a space repo, and the server that stores it a repo host.)

And, there are no relays and no firehose for spaces. So, something needs to tie the space together. That is the space host.

(For more on spaces, see: ATProto Syncer.)

What a Space Host Is Not

It is easy to imagine that a space host stores all the records in a space. It does not.

The proposal says:

The space host (if distinct from the repo host) never hosts or distributes record data, only repo update metadata.

A space host knows who has records in the space, and when they changed — but not what the records are. The records themselves always come from the repo hosts.

Finding the Space Host

Every space has a space authority — the DID at the start of its at:// URI. That DID might be a user's own DID (for example, for their bookmarks). Or, it might be a DID made just for the space (for example, for a forum).

To find the space host, resolve the space authority's DID exactly like any other account's — the #atproto_pds service in its DID document is the space host. (See: How-To Resolve a DID to a PDS.)

The proposal says:

A space authority is resolved like any other atproto account. Its #atproto_pds service endpoint is the space host, and its #atproto key signs the space's credentials and any service auth it sends as the authority.

So, usually, a space host is just a PDS. (A PDS is usually both a repo host for its accounts, and a space host for the spaces owned by its accounts.) But, it does not have to be — any service that implements the required XRPC API end-points can be a space host.

Job 1: Deciding Who May Read

To read a space, an application needs a token called a space credential. The space host is what hands these out.

An application asks for a space credential by calling com.atproto.space.authorizeSpaceSync on the space host. The request can include 2 kinds of proof:

delegation token — which user

proof that a particular user has authorized this application. It is made by the user's PDS, is signed with the user's #atproto key, is addressed (aud) to the space host, can only be used once, and expires after 60 seconds (by default).

client attestation — which application

proof of which application is asking. It is signed by the application's own key. The space host checks it by fetching the application's client-metadata.json, and the public-keys listed there.

A space might require either one, both, or neither. (The proposal says a space host “MUST NOT reject a request solely because it includes a valid assertion that the space does not require.”)

Then the space host decides: yes or no. How it decides is not part of the core protocol. It is decided by the space's policy (see below).

If the answer is yes, the space host returns a space credential. A space credential is a JWT, signed with the space authority's #atproto key:

iss

the space authority.

sub

the space that may be read.

cnf.kid

the public-key the application sent as credentialKey. This ties the space credential to the application — only whoever holds the matching private-key can use it.

exp

when it expires — 10 minutes after it was issued, by default (and at most 60 minutes).

jti

a unique identifier — used if the space credential needs to be revoked.

Since the space credential is signed with the space authority's key, any repo host can check it by itself — without asking the space host.

The space host also returns the space's current revision (spaceRev).

Taking Access Away

The main way a space host takes access away is simple — it stops saying yes. Since a space credential is short-lived, the application soon loses access.

If that is not fast enough, the space host may call com.atproto.space.notifyCredentialsRevoked on the repo hosts in the space, listing the jti of each revoked space credential. It is up to the space host to decide when this is worth doing. (For a small space it is cheap, for a huge one it is not.)

Job 2: Keeping Track of Who Has Written

Because the records in a space are spread across many repo hosts, an application needs to know whose space repos to pull. The space host keeps that list. It is called the writer set.

Here is how it works. Whenever a user writes a record to a space, the user's PDS (the repo host) calls com.atproto.space.notifyRepoUpdate on the space host, with the space repo's new revision (repoRev) and digest (data).

When the space host receives one of these, it:

  • checks the caller, using service auth,
  • rejects it if the account is not allowed to write to the space,
  • ignores it if the repoRev is not newer than the one it already has (or is in the future), and
  • otherwise, records the space repo's new state.

(The space host is not expected to check the data digest — it does not have the records to check it against.)

Applications get the writer set by calling com.atproto.space.listWriters on the space host. For each account, it returns the space repo's current repoRev and data. An application can also ask for only the changes since some earlier space revision.

A few things to note:

  • The writer set is not a member list. It only lists accounts that have written at least one record. People who are only allowed to read are never listed.
  • The space authority is always part of the writer set.
  • An account can be removed from the writer set — for example, if it loses write access, or with com.atproto.space.removeWriter. Removals are sequenced like writes.
  • The space host MAY “garbage collect” empty and removed entries — but SHOULD wait at least 72 hours first.
  • The space host decides which writers it tracks. It may leave out (or rate-limit) any of them — for example, for spam.

Job 3: Telling Syncers When Something Changes

An application that keeps its own copy of a space is called a syncer. Rather than making every syncer check every space repo over and over again, the space host tells them when something changes.

Registering

A syncer registers for notifications by including a notify object when it calls authorizeSpaceSync:

Before creating a new registration, the space host checks that the endpoint really wants it. It calls com.atproto.space.confirmRegistration on the endpoint, with the token, the space, and a random challenge. The syncer must echo the challenge back. If it does not, the space host rejects the request.

A registration is identified by its endpoint and token together. Each time a syncer calls authorizeSpaceSync again with the same pair, the registration is renewed.

Notifying

When the space host gets a valid notifyRepoUpdate, it calls com.atproto.space.notifySpaceUpdate on every registered syncer.

The space host gives the space as a whole its own revision (a TID), which goes up with every change. Each notification includes both the current and the previous space revision. That way, a syncer can tell if it missed one.

Notifications contain no records. They only say that a space repo has a new revision, or that an account was removed from the writer set, or that something happened to the space itself (such as being deleted).

For ordinary updates, the space host only needs to make a “reasonable-effort” to deliver them. (If a syncer misses one, it can catch up with listWriters.)

Expiring

A registration stays active only while the space credential from the syncer's latest authorizeSpaceSync is still valid. After that, the registration lapses.

The next time the space changes (however long after), the space host sends the lapsed syncer a notification saying that its registration has expired — instead of the update. And then, nothing more (other than a deletion notice), until the syncer calls authorizeSpaceSync again.

Unlike ordinary updates, the space host is responsible for reliably delivering this expiry notice — retrying with exponential backoff for at least 72 hours. If it still cannot deliver it, it may drop the registration.

Policies

How does a space host decide who may read, and whose writes to track? The core protocol does not say. Instead, each space has a policy.

A policy is a JSON object, identified by its $type. For example:

Every PDS MUST support these 3 baseline policies:

com.atproto.personalspace.policy

only the space authority's own account has access. For personal data, such as bookmarks, mutes, or drafts.

com.atproto.memberspace.policy

access is checked against a member list kept by the PDS. Each member has a read and a write true/false value. It also has options to let anyone read (publicRead), let anyone write (publicWrite), and limit which applications may read (allowedApps). The member list is managed with com.atproto.memberspace.putMembers, removeMembers, and listMembers.

com.atproto.managedspace.policy

the decision is handed off to an outside service — the managing app. The space host asks it by calling checkAccess on it. This allows rules like “only people I follow” or “only paying subscribers”, without the PDS having to keep a member list.

Under every policy, the space authority's own account is always allowed to read and write.

A space host may support other policies too. If asked to use a policy it does not support, it MUST fail with an UnsupportedPolicy error.

By default, a space's policy and member list are private — only the space authority can see them. But, memberspace and managedspace have a publishPolicy flag, and memberspace also has a publishMembers flag. When set, the space host publishes that information as records in the space authority's own space repo, so that readers can see it. It is the space host's job to keep those records in sync with the actual configuration.

Deleting a Space

When a space is deleted, the space host:

  1. stops issuing space credentials for it,
  2. deletes all the records in the space authority's own space repo,
  3. notifies every registered syncer — including ones whose registrations have lapsed — reliably, and
  4. answers any later authorizeSpaceSync for that space with a SpaceDeleted error.

The space host SHOULD remember the deletion until every syncer that was registered at the time has been notified (or had its registration dropped).

Note that the space host does not delete other users' records. Those belong to the users. They just become unreadable to everyone but their owners.

Other Responsibilities

takedowns and deactivation

If the space authority's account is taken down or deactivated, its spaces are suspended. The space host answers authorizeSpaceSync and listWriters with RepoTakendown or RepoDeactivated. Registrations lapse, but are not dropped. (This is not the same as deleting the space.)

account migration

A space host holds some state that is not stored as records — such as a space's policy and member list. When the space authority's account moves to a new PDS, this is moved as a space meta archive, using com.atproto.space.exportSpaceMeta and importSpaceMeta. Notification registrations are not moved — syncers re-register when they notice the #atproto_pds has changed.

Summary

An ATProto space host:

  1. is found by resolving the space authority's DID to its #atproto_pds (usually it is just a PDS),
  2. decides who may read the space, according to the space's policy, and issues short-lived space credentials,
  3. keeps the writer set up-to-date, from notifyRepoUpdate calls made by repo hosts,
  4. notifies registered syncers when something changes, and
  5. never stores or hands out the records themselves.

Again, this is all a proposal. Details are likely to change.
