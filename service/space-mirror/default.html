ATProto Space Mirror

one syncer that keeps a copy of a permissioned “space”, and serves it to your other services

by Charles Iliya Krempeaux

A space mirror is an internal service that does 2 things:

  1. it is a syncer — it keeps its own copy of a space up-to-date, by pulling from the repo hosts, and
  2. it serves that copy to your own other services, using the same kind of XRPC API end-points that a repo host has — getRecord, listRecords, getBlob, listBlobs, getLatestCommit, getRepo, and listRepoOps.

A space mirror is not a repo host, and it is not a public service. To the rest of the network, it is just one syncer. Only your own services can call its repo host-style end-points — and they trust it, because they are part of the same system.

Note! Spaces are a proposal — proposal 0016, “Atproto Spaces”. They are not (yet) part of the ATProto specification. The proposal itself says:

This is a proposal, not the final specification. Details, terminology, and behaviors are all likely to change.

And, a space mirror is not in the proposal at all. It is not a protocol role. It is a way of building an application on top of the protocol — splitting the syncer part of an application out into its own service. This article describes the proposal as of November 2026.

Why Have a Space Mirror?

A real application is often several services. For example, an application for private forums might have:

  • an AppView that shows the forums to users,
  • a search indexer,
  • a notification service, and
  • moderation tools.

All of them need the data in the space. If each one were its own syncer, then each one would need its own space credentials, its own notification registrations, and its own copy of every space repo — pulled separately from every user's PDS.

That matters, because spaces have no relays. Every syncer pulls directly from the users' PDSes. The proposal says:

The one major difference is the lack of relays. Applications sync space repos directly from PDSes rather than relying on an intermediary service, which places additional load on PDSes.

And:

Second, sync load scales with the number of applications syncing a space, not the number of end users. An application serving many users pulls each repo once and fans it out to them from its own copy, which keeps the number of distinct syncers per repo relatively low.

A space mirror is that idea, applied to an application made of several services. The application pulls each space repo once (through the space mirror), and fans it out to its own services from that one copy.

About the Name

Why “mirror”? A mirror keeps a full copy of something, keeps that copy up-to-date, and answers requests from it — usually through the same kind of interface as the original. That is exactly what a space mirror does.

Why “space”? Because what it keeps a copy of is a space. (In English, an “X mirror” is a mirror of X — like a “Debian mirror”.)

It is not a proxy. A proxy passes each request on to the real server, as it happens. (ATProto uses the word this way — service proxying, with the atproto-proxy header, forwards a request to another service. See: ATProto AppView.) A space mirror never passes a request on. It answers every request from its own copy, which it keeps up-to-date ahead of time.

Two things the name does not say:

  • it is internal. Many mirrors (for example, software mirrors) are public. A space mirror must not be. (See “Why It Must Stay Internal”, below.)
  • it copies from many places. A space is spread across every member's repo host. So, a space mirror is not a copy of one server — it gathers many users' space repos into one place.

Two Faces

A space mirror has 2 faces — one facing the network, and one facing your own services.

Facing the Network: a Syncer

Toward the network, a space mirror is an ordinary syncer. It does everything a syncer does:

  1. gets a space credential from the space host, with com.atproto.space.authorizeSpaceSync (and gets a new one before it expires),
  2. finds out who has written to the space, with com.atproto.space.listWriters,
  3. pulls each space repo from its repo host, with com.atproto.space.listRepoOps (or getRepo, to start from nothing),
  4. registers for, and receives, notifications (com.atproto.space.notifySpaceUpdate and confirmRegistration), and
  5. checks that the data is real — the MACs and the digests.

(For the details, see: ATProto Syncer.)

Note that the notification end-points must be reachable from the internet, since the space host calls them. It is only the other face that is internal.

How It Differs from a Real Repo Host

The end-points may look the same. But, they do not promise the same things:

The missing MACs are the important one. A MAC is computed with the author's #atproto_kem private key — and the proposal says “The repo host holds the private key.” A space mirror does not have it, so it cannot make a valid MAC.

That is fine internally. The space mirror checks the MACs when it pulls from the real repo hosts. After that, your services trust the space mirror — the same way they would trust their own database.

Why It Must Stay Internal

It might be tempting to let other applications use a space mirror too. That runs into problems:

nobody can check its data

Without MACs, an outside application would have to just trust it. And, that is on purpose. The proposal says permissioned data “should not carry proof of authorship that survives a leak outside its access boundary, so space repos do not use signatures.” Public data is signed, so anyone can pass it on and anyone can check it. Space data is not.

nobody can find it

Applications find a space repo by resolving the author's DID to its #atproto_pds. There is no way to advertise a copy somewhere else.

it misses revocations

A space host sends com.atproto.space.notifyCredentialsRevoked to the “repo hosts serving repos in the space”. It does not know about a space mirror. So, a space mirror checking outside applications' space credentials would keep accepting revoked ones until they expire (up to 60 minutes).

it is handed replayable credentials

When a space credential is used, the HTTP Message Signature covers only the Authorization and Atproto-Space-Audience headers — and when syncing, the audience is the repo owner's DID, not the server's. The proposal says “Replay against the same audience is allowed.” So, every request an outside application sent to a space mirror could be replayed against the real repo host, until it expires.

it goes against the design

The proposal says “Public broadcast is built for open distribution (signed, archival, rebroadcastable) while atproto spaces are built for party-to-party transmission within an access boundary.” The space authority let your application sync the space. That is not the same as letting your application pass it on to others.

None of these are problems when every caller is part of your own application.

Responsibilities

A space mirror has every responsibility a syncer has. But, because other services serve users from its copy, it also has to make sure those responsibilities reach them.

Keep It Internal

Do not expose the repo host-style end-points to the internet, and do not list them in any DID document. Protect them with internal authentication — a private network, mTLS, an internal token, etc.

One Credential per Space, Not per Service

The space mirror should hold one space credential and one notification registration per space, for your whole application. That is the point — one copy, pulled once.

It also needs whatever authorizeSpaceSync requires for that space. That might be a delegation token (made by a user's PDS, through that user's OAuth session with your application), a client attestation (signed with your application's client key), or both. The proposal says one user's session is enough:

An application serving several users of a space does not necessarily need to maintain a space credential for each user. It may obtain its credential using any one user's session.

So, the space mirror needs a way to get delegation tokens from whichever of your services holds your users' OAuth sessions.

Per-User Access Stays with Your Services

A space credential lets your application sync a space. It does not say which of your users may see it. The proposal puts that on “the syncing application” — which, now, means your services that face users. They must still check, for each user, whether that user may see each space.

The proposal says that “is not a signal for syncers to drop the space's data”. But, it should not be served — the proposal also says “inactivation of an account impacts all data from all accounts in spaces under their authority”.)

Pass Changes Downstream

When the space mirror deletes a space, clears a space repo, removes a writer, or sees an account's status change, it should tell your services. Otherwise, copies further downstream (search indexes, caches, etc) keep serving data that should be gone.

Follow the Firehose

Account status (active, deactivated, taken down, deleted) is announced on the firehose, not through spaces. The proposal says that even an application that syncs only spaces “still needs to subscribe to a firehose to receive #account and #identity events.” So, the space mirror should subscribe to one (from a relay), and:

  • stop serving a deactivated or taken down account's data,
  • delete a deleted account's data, and
  • notice when an account's #atproto_kem key or PDS changes.

Respect Takedown Labels

The proposal says that “space authorities may publish !takedown labels to remove content from their spaces, and synchronizing services and client apps should respect such takedown labels.” Those labels are records in the space, so the space mirror will have them. Decide whether the space mirror itself stops serving the labeled content, or whether your services do. (See: ATProto Labeler.)

Here is the internal face of a space mirror, in Go. It serves getRecord from a local copy — and keeps track of which spaces it may serve, and which accounts are not active. (The syncer face, which fills in the local copy, is not shown. See: ATProto Syncer.)

A few things to note:

  • It only listens on 127.0.0.1, and requires an internal token (from the INTERNAL_TOKEN environment variable). It refuses everything if no token is set.
  • It returns no MAC, and does not ask for a space credential.
  • The syncer face calls setServing after each authorizeSpaceSync (true for a new credential, false for access denied), deleteSpace on SpaceDeleted, and setAccountStatus on each firehose #account event.
  • The parameter names (space, repo, collection, rkey), the SpaceNotFound error, and the response shape are this article's choices. There are no published lexicons for spaces yet — and, since this is internal, they are yours to decide anyway. (RepoDeactivated and RecordNotFound are the error names used for public repos — and the proposal says space sync errors “should have the same error names as for public repo sync responses”.)
  • A record's URI is the space's URI, then the author's DID, collection, and record key — for example, at://did:example:forum/space/com.atmoboards.forum/general/did:example:alice/com.atmoboards.thread/3mwcj3b6uak2f (an example from the proposal).
  • A real one would use a database rather than memory, and would serve the other 6 end-points too.

This code was tested with Go's httptest, by stepping a record through: not yet authorized (404), authorized (200), wrong token (401), account deactivated (400 RepoDeactivated), reactivated (200), access denied (404), re-authorized (200), and space deleted (404, with no records left).

Summary

An ATProto space mirror:

  1. is an internal service — not a protocol role, and not in the proposal,
  2. is an ordinary syncer to the rest of the network (one credential, one registration, one copy, per space),
  3. serves its copy to your own services, through repo host-style end-points,
  4. cannot make MACs, is not the source of truth, and cannot be found through DID documents — which is why it must stay internal,
  5. leaves per-user access checks to your services, and
  6. must pass deletions, access changes, and account status changes on to your services.

Again, spaces are a proposal. Details are likely to change.
