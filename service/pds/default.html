ATProto Personal Data Server (PDS)

the server where an account — and its data — lives

by Charles Iliya Krempeaux

A Personal Data Server (PDS) is a type of AT-Protocol (ATProto) service that hosts accounts. It is one of the 3 core services of ATProto — along with relays and AppViews.

The ATProto overview puts it this way:

Personal Data Servers are your home in the cloud. They host your data, distribute it, manage your identity, and orchestrate requests to other services to give you your views.

And, the glossary says:

A PDS, or Personal Data Server, is a server that hosts a user. A PDS will always store the user's data repo and signing keys. It may also assign the user a handle and a DID. Many PDSes will host multiple users.

A user's PDS is the source of truth for that user's data — everything else in the network (relays, AppViews, etc) only has copies. But, a PDS does not show you the rest of the network. It only has its own accounts' data. For everyone else's posts, likes, follower counts, etc, it forwards your app's requests to an AppView.

(Note that “personal” does not mean one server per person. Most PDSes host many accounts.)

What a PDS Does

The accounts specification lists the main things:

All users in the atproto network have an "identity", based around a unique and immutable DID. Active users also have an "account" on a Personal Data Server (PDS). The PDS provides a number of network services, including repository hosting, authorization and authentication, and blob storage.

So, a PDS has these jobs:

  1. hosting each account's repository (its records),
  2. storing each account's BLOBs (images, videos, etc),
  3. logging users in (authentication and authorization),
  4. managing each account's identity (its signing key, and often its handle and DID),
  5. telling the network about changes (its firehose), and
  6. forwarding requests to other services (service proxying).

Job 1: Hosting Repositories

Each account's public data is stored in a repository — a collection of records (posts, likes, follows, profile, etc), grouped by collection (app.bsky.feed.post, app.bsky.feed.like, etc).

Each change to a repository makes a new commit, which is signed with the account's signing key. The repository specification says:

Commits are cryptographically signed, with rotatable signing keys, which allows recursive authentication of either the repository structure as a whole, or compact "proof chains" for individual records.

The PDS holds the private signing key, so that it can make those commits on the user's behalf. And, since every commit is signed, anyone can check a copy of the data — no matter who they got it from — against the public key in the DID document. That is what lets relays and AppViews pass the data around.

Job 2: Storing Blobs

Images, videos, and other files are not stored inside records. They are stored separately, as BLOBs, and records refer to them by CID (a hash).

  • An app uploads a BLOB with com.atproto.repo.uploadBlob, then creates a record that refers to it.
  • Anyone can download it with com.atproto.sync.getBlob, and list an account's BLOBs with com.atproto.sync.listBlobs.

The uploadBlob lexicon says “The blob will be deleted if it is not referenced within a time window (eg, minutes).” So, upload first, then create the record soon after.

A PDS sets its own size limit — blobUploadLimit, in describeServer. (puffball.us-east.host.bsky.network says 314572800 bytes — 300 MB — which is also the default for Bluesky's PDS software.)

Job 3: Logging Users In

Apps write to a user's repository by making authorized requests to the user's PDS. The main way to get authorized is OAuth. The OAuth specification says:

OAuth is the primary mechanism in atproto for clients to make authorized requests to PDS instances.

In OAuth terms, the PDS is always the Resource Server (the server the requests go to). The Authorization Server (the server that does the login) might be the PDS itself — or a separate service, which the specification calls an entryway:

Sometimes the PDS is also the "Authorization Server" - which services OAuth authorization flows and token requests - while in other situations a separate "entryway" service acts as the Authorization Server for multiple PDS instances.

The PDS also handles the rest of the account itself — creating it (com.atproto.server.createAccount), email confirmation, password resets, deactivating, and deleting. Most of that is under com.atproto.server.*.

Job 4: Managing Identity

An account's identity is its DID (and its handle). The PDS is closely involved:

  • It holds the account's signing key (the #atproto key in the DID document).
  • For a did:plc, it often creates the DID, and can update its DID document (for example, with com.atproto.identity.updateHandle, signPlcOperation, and submitPlcOperation).
  • It may give the account a handle under one of its availableUserDomains — or the user can use their own domain.

But, the identity is not owned by the PDS. The overview says:

The signing key is entrusted to the PDS so that it can manage the user's data, but rotation keys can be controlled by the user, e.g. as a paper key. This makes it possible for the user to update their account to a new PDS without the original host's help.

(The accounts specification also warns: “Users should take special care to select and assess their PDS host when they delegate management of their identity to that host (eg, when using a did:plc).”)

Job 5: Telling the Network About Changes

A PDS publishes every change to every account it hosts, as an event stream — its own firehose — at com.atproto.sync.subscribeRepos. The sync specification says:

PDS hosts provide a firehose that includes updates for all hosted accounts.

Relays subscribe to many PDS firehoses, and combine them into one. A PDS asks relays to subscribe to it by calling com.atproto.sync.requestCrawl on them. (In Bluesky's PDS software, the PDS_CRAWLERS setting lists which relays to ask; the default is https://bsky.network.)

The firehose also carries #identity events (when a handle or DID document changes), and #account events (when an account's status changes).

Job 6: Forwarding Requests (Service Proxying)

A PDS only has its own accounts' data. So, when an app asks for something like a timeline, a thread, or a profile with follower counts, the PDS forwards the request to another service — usually an AppView. The HTTP API specification says:

The PDS acts as a generic proxy between clients and other atproto services. Clients can use an HTTP header to specify which service in the network they want the request forwarded to (eg, a specific AppView or Labeler service). The PDS will do some safety checks, then forward the request on with an inter-service authentication token (JWT, described above) issued and signed by the user's identity.

The header is atproto-proxy. For example:

For proxying to happen, the request must be from a logged-in user with an active account on the PDS, it must be for an /xrpc/ end-point, and the target service must have a resolvable DID with a matching service entry.

Account Status

On a PDS, each account is either active or not. If it is not active, the specification lists a more specific status:

deleted

the user or host deleted the account; its content should be removed from the network.

deactivated

the user paused the account, for a while. (Also the starting state of an account that is migrating to a new PDS.)

takendown

the host (or another service) took the account down.

suspended

the host (or another service) paused the account, for a while.

(There are also desynchronized and throttled, where the account may still be active.)

Moving to Another PDS

A user is not stuck with their PDS. The overview says:

We assume that a Personal Data Server may fail at any time, either by going offline in its entirety, or by ceasing service for specific users. The goal of the AT Protocol is to ensure that a user can migrate their account to a new PDS without the server's involvement.

An account has moved once its DID document points to the new PDS, it is active there, and it has a working repository there. When both the old and new PDS are working, the accounts specification summarizes the steps as:

  1. create an account on the new PDS (which may start out not active),
  2. copy the data from the old PDS to the new one,
  3. update the DID document to point to the new PDS, with a new signing key,
  4. make the old account inactive, and the new one active, and
  5. publish a new commit from the new PDS, signed with the new key.

This is why backups matter. If a PDS disappears without notice, a user with a backup (and control of their DID) can upload it to a new PDS. (See: How-To Backup an ATProto PDS.)

A PDS and Spaces

There is a proposal to add permissioned (non-public) data to ATProto — spaces. Under that proposal, a PDS usually plays 2 more roles:

  • a repo host — storing and serving its accounts' records in spaces, and
  • a space host — answering for the spaces its accounts are the authority of.

(This is a proposal, and not yet part of the specification.)

Running Your Own PDS

Anyone can run a PDS. Bluesky publishes its PDS software, with instructions, at github.com/bluesky-social/pds. (The code itself is in TypeScript.)

A few things from its instructions worth knowing:

  • A PDS has a health-check end-point — /xrpc/_health. For example, blacksky.app answers {"version":"1.14.19","gatekeeper_version":"1.0.2-blacksky"}.
  • WebSockets must work, or the network will not see the PDS's changes. (The firehose is a WebSocket.)
  • Once running, it “will automatically begin broadcasting events to Relay servers.” So, to change a PDS's hostname, migrate the accounts one by one — do not just wipe and reinstall.

Summary

An ATProto Personal Data Server (PDS):

  1. hosts accounts — usually many of them,
  2. is found through the #atproto_pds service in an account's DID document,
  3. is the source of truth for its accounts' repositories, which it signs with each account's signing key,
  4. stores its accounts' BLOBs,
  5. logs users in (with OAuth — itself, or through an entryway),
  6. publishes every change on its firehose, for relays,
  7. forwards requests for everything else to other services, such as AppViews, and
  8. can be left — an account can move to another PDS.
