ATProto Repo Host

the service that stores and serves users' records in permissioned “spaces”

by Charles Iliya Krempeaux

A repo host is a type of AT-Protocol (ATProto) service that stores users' records for spaces, and serves them to applications that are allowed to read them.

The proposal that defines it puts it this way:

Repo host: a service that stores and serves users' space repos.

In practice, a user's repo host is just their Personal Data Server (PDS) — the same server that already holds their public data. It is not usually a separate server. “Repo host” is the name for one of the roles a PDS plays.

The proposal says:

A PDS fulfills both the roles of a repo host and a space host. However, these roles are discussed separately because they do not necessarily need to be filled by a PDS.

But, note that the data a repo host serves is not the user's ordinary public repository. It is a separate, different kind of repository — a space repo. A user has one ordinary public repository, plus one space repo for each space they have written to.

Note! At the time of writing, spaces and repo hosts are a proposal — proposal 0016, “Atproto Spaces”. They are not (yet) part of the ATProto specification. The proposal itself says:

This is a proposal, not the final specification. Details, terminology, and behaviors are all likely to change.

This article describes the proposal as of November 2026.

Spaces, Briefly

A space is a group of records that only some people (and some applications) are allowed to read — for example: a private forum, a paid newsletter, or a user's bookmarks.

The records in a space are spread out. Each user stores their own records for a space on their own repo host.

There are 3 roles involved:

repo host

stores and serves each user's records for a space. (This article.)

space host

answers for a space as a whole — who may read it, who has written to it, and who to notify when it changes.

syncer

an application that keeps its own copy of a space, by pulling from the repo hosts.

Of these 3, the repo host is the only one that is the source of truth for the records themselves. The space host only knows who has records, and when they changed. The syncer only has a copy.

Space Repos

A space repo is one user's records in one space.

Like an ordinary ATProto repository, it is a key/value store:

  • each key is a path — a collection NSID and a record-key, such as com.atmoboards.thread/3mwcj3b6uak2f, and
  • each value is a record.

Creating and Clearing

There is no “create a space repo” operation. A user's space repo is created automatically, the first time they write a record to that space.

There is also no “delete a space repo” operation. Instead, a space repo can be cleared — all its records deleted at once — with com.atproto.space.clearRecords. An empty space repo and a non-existent one are treated as the same thing.

(Why clear rather than delete? Because the repo host still needs to be able to answer syncers with a valid commit that shows the records are gone.)

A repo host MAY “garbage collect” an empty space repo — but SHOULD wait at least 72 hours after it was cleared, so the change has time to reach the space host and the syncers.

The Commit

Each space repo has a commit. The commit summarizes the whole space repo, so that a syncer can check whether its copy matches — without downloading everything again.

A commit has these fields:

ver

the commit format version — currently 1.

repo

the DID of the user whose space repo this is.

space

the space's URI — at://authority/space/type/skey.

rev

the revision — a TID, which goes up with every change.

data

a 32-byte digest of all the records in the space repo.

The Digest: LtHash

The data digest is computed using a set hash called LtHash.

A set hash has 2 useful properties:

  • it does not depend on the order records were added — 2 space repos with the same records always have the same digest, and
  • adding or removing a single record is cheap — you do not need to re-hash everything.

This means a repo host can keep the digest up-to-date with each write. (And, so can a syncer, as it applies each change to its copy.)

Here is how it works:

  1. The state is 2048 bytes — used as 1024 little-endian unsigned 16-bit numbers (“lanes”). It starts out as all zeros.
  2. Each record becomes one element — the string collection/rkey/record_cid.
  3. To add an element: expand it to 2048 bytes using BLAKE3 in XOF (extendable-output) mode, read those bytes as 1024 little-endian uint16 lanes, and add each lane to the matching state lane (wrapping around at 65536).
  4. To remove an element: do the same, but subtract instead of add.
  5. The commit's data is the SHA-256 of the 2048-byte state.

Serving Space Repos

A repo host lets applications read space repos through these XRPC API end-points:

com.atproto.space.getRecord

get a single record.

com.atproto.space.listRecords

list the records in a space repo. (Set excludeValues to get only the paths and CIDs.)

com.atproto.space.getLatestCommit

get the current commit.

com.atproto.space.listRepoOps

get the changes since a given revision. (The main way syncers stay up-to-date.)

com.atproto.space.getRepo

download the whole space repo, as a STAR file.

com.atproto.space.listBlobs

list the BLOBs referred to by records in a space repo.

com.atproto.space.getBlob

download a single BLOB.

Who May Read

Each of these end-points accepts either:

  • an OAuth session from the user's own application (with a covering space: scope) — for reading the user's own space repo, or
  • a space credential — for reading any space repo in the space.

A space credential is a short-lived token, signed by the space authority, and issued by the space host. The repo host can check it by itself — it does not need to ask the space host.

When it gets one, the repo host MUST check (among other things):

  • the space credential itself — its type, issuer, signature, space, and expiration,
  • that there is exactly one signature with the tag atproto-space-credential, covering exactly ("authorization" "atproto-space-audience"),
  • that the signature was made with the key in the space credential's cnf.kid (a P-256 did:key), and
  • that Atproto-Space-Audience is the DID of the space repo's owner.

A repo host MUST also reject any space credential that the space authority has revoked. (The space host sends revocations with com.atproto.space.notifyCredentialsRevoked, identifying each space credential by its jti. The repo host must remember each revocation for at least 60 minutes.)

The Operation Log

To support listRepoOps, a repo host keeps an operation log of recent writes to each space repo. Each entry has:

cid is null for a delete, and prev is null for a create. Changes made together (atomically) share the same rev.

By default, listRepoOps includes each created or updated record's value — so a syncer does not need to call getRecord for each one. Every response also includes the current commit.

The operation log is only an optimization. A repo host may shorten it, or drop it — keeping only some recent window. (A syncer that asks for a revision that is no longer in the log falls back to downloading the whole space repo with getRepo.)

STAR Files

getRepo returns the whole space repo as a STAR file. A STAR file is a header followed by a sequence of key/value pairs:

  • the magic bytes are 0x2A 0x6C 0x01 0x00,
  • each len is an unsigned varint,
  • the metadata contains $type (atproto-space-repo) and all the fields of the commit,
  • each path is collection/rkey, and each record is the record's canonical DRISL encoding,
  • records MUST be in strict lexicographic order of their path bytes, with no duplicates.

Because the commit's digest is in the header, a reader can check the whole file as it streams it in — by computing the LtHash as it goes, and comparing at the end.

Proving the Data Is Real

Records in a public repository are proven with a signature. Anyone can check it.

For space repos, that would be a problem — if private data leaked, the signature would prove it was real. So, space repos do not use signatures.

Instead, each request gets a temporary shared secret between the syncer and the repo host. The repo host uses it to compute a MAC over the commit (or record). The syncer can check the MAC. But, since the syncer knows the secret too, the MAC proves nothing to anyone else.

To make this work, the repo host:

  1. holds a dedicated P-256 key-pair for each account — the KEM key — and publishes its public-key in the account's DID document, with the id DID#atproto_kem. (This should be a different key from the #atproto signing key.)
  2. reads the syncer's temporary public-key from the keyid in its Accept-Signature header,
  3. combines it with the KEM private-key to get the shared secret (using HPKE secret export, RFC 9180), and
  4. returns an hmac-sha256 HTTP Message Signature over an Atproto-Space-Commit (or Atproto-Space-Record) header.

Notifying the Space Host

Whenever a user writes to a space repo, the repo host tells the space host, by calling com.atproto.space.notifyRepoUpdate on it, with the space repo's new repoRev and data. (Unless the user is the space authority.)

A few rules:

  • no registration is needed — it is automatic,
  • the call is authenticated with service auth,
  • the repo host is responsible for reliably keeping the space host up-to-date — retrying network failures and temporary HTTP errors with exponential backoff (but stopping on permanent errors),
  • repoRev must always go up, and must not be in the future.

A user's repo host does not need to check whether a space exists before accepting a write to it. (Unless the user is also the space authority — in that case, the space must already exist.)

Other Responsibilities

writing records

When the repo host is a PDS, it also lets the user's own applications (through OAuth) write to their space repos — with com.atproto.space.createRecord, putRecord, deleteRecord, applyWrites, and clearRecords. (Writes only accept OAuth — never a space credential — since a write belongs to the user who made it.)

takedowns

A repo host answers with the same errors as for public data — such as RepoTakendown for a taken-down account, and RepoDeactivated for a deactivated one. An account takedown affects all of the account's space repos.

account migration

When an account moves to a new PDS, each space repo is exported from the old one with com.atproto.space.getRepo, and imported into the new one with com.atproto.space.importRepo. The new repo host may give it a new rev, but its data stays the same. The new repo host also makes its own KEM key, and publishes it in the account's DID document. (The operation log starts fresh.) Even a taken-down account should still be able to export its space repos, so that it can move away.

Summary

An ATProto repo host:

  1. is usually just the user's PDS,
  2. stores the user's space repos — one per space, separate from their public repository,
  3. keeps an LtHash digest of each space repo, in its commit,
  4. serves space repos to the user's own apps (with OAuth) and to syncers (with a space credential),
  5. proves the data with a MAC, not a signature, and
  6. tells the space host about every write.

Again, this is all a proposal. Details are likely to change.
