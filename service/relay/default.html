ATProto Relay

the service that combines many firehoses into one

by Charles Iliya Krempeaux

A relay is a type of AT-Protocol (ATProto) service that listens to the changes happening on many Personal Data Servers (PDSes), and combines them into a single stream of changes — called a firehose.

The ATProto specification puts it this way:

Relays are network services which subscribe to multiple upstream firehoses (eg, multiple PDS hosts) and aggregate them in to a single combined event stream. A relay which attempts to aggregate accounts from all PDS instances in the network outputs a "full-network" firehose.

A relay is not where users' data lives. The data lives on each user's PDS. A relay just passes changes along — from many PDSes, to whoever is listening.

And, a relay is a separate service that applications use. (Compare this with a syncer, which is the application.)

Why Relays Exist

Every PDS has its own firehose — a stream of every change to every account it hosts.

An application that wants to see what is happening on the whole network (for example, an AppView that shows posts from everyone) could connect to every PDS's firehose itself. But, there are thousands of PDSes. So, that would mean thousands of connections — for every application.

A relay does that work once, and shares the result. Each application then only needs one connection — to a relay.

Note that a relay is an optimization. It is not required. The ATProto glossary says:

Relays are an optimization and are not strictly necessary. An AppView could communicate directly with PDSes (in a smaller-scale application). The Relay serves to reduce the number of connections that are needed in the network.

Relays You Can Connect To

Anyone can run a relay. And, there is more than one. Here are some that were working at the time of writing:

bsky.network

Bluesky's relay. (Bluesky also runs relay1.us-east.bsky.network and relay1.us-west.bsky.network.)

relay.fire.hose.cam

a relay whose home page says it is running the relay codebase from Bluesky's indigo repository.

atproto.africa

the Blacksky team's relay. (Its home page says “RSKY RELAY”.) (At the time of writing, it answered listHosts and getHostStatus, but not listRepos or getRepoStatus.)

Different relays may crawl different sets of PDSes. So, they do not necessarily all have the same data.

The Firehose

The firehose is the com.atproto.sync.subscribeRepos XRPC API end-point. Both a PDS and a relay implement it, in the same way. (A PDS's firehose has the changes for its own accounts. A relay's firehose has the changes for all the accounts on all the PDSes it follows.)

It is a WebSocket, rather than an ordinary HTTP request. For example: 


wss://bsky.network/xrpc/com.atproto.sync.subscribeRepos

It is public. It does not require logging in.

Frames

Each WebSocket frame contains 2 CBOR objects, one right after the other:

header

op is 1 for a normal message, or -1 for an error. t is the type of the message — such as #commit.

message

the event itself. Its shape depends on t.

A single frame can be at most 5 megabytes.

Event Types

There are 4 main types of event:

#commit

a change to an account's repository — records created, updated, or deleted. It includes the list of operations (ops), the new signed commit, and the changed data blocks (as a CAR slice). So, an application does not need to go and fetch the change from the PDS.

#sync

the account's repository has been reset to a new state — so any copy of it should be re-synced.

#identity

the account's DID document or handle may have changed.

#account

the account's hosting status has changed — active is true or false, and status may be takendown, suspended, deleted, or deactivated.

(There is also #info, for informational messages — such as telling a client that its cursor is too old.)

Sequence Numbers and Cursors

Every event has a seq — a sequence number, that goes up with each event.

If a client disconnects, it can reconnect with a cursor query parameter, set to the last seq it saw, to pick up where it left off: 


wss://bsky.network/xrpc/com.atproto.sync.subscribeRepos?cursor=35746373394
  • with no cursor, the stream starts from now,
  • with a cursor inside the server's “roll-back window”, the server sends the events since then, and then continues live,
  • with a cursor older than the roll-back window, the server says so (with an #info message), and starts from the oldest event it still has,
  • with a cursor in the future, the server sends an error (FutureCursor), and closes the connection.

Note that seq numbers belong to a particular server. A seq from one relay means nothing to a different relay (or to a PDS).

The roll-back window is limited. It is for catching up after a short disconnection — not for replaying the whole history of the network.

If a client cannot keep up with the stream, the server may send a ConsumerTooSlow error, and close the connection.

Other XRPC API End-Points

Besides the firehose, a relay has a few more XRPC API end-points:

com.atproto.sync.listHosts

lists the upstream hosts (PDSes, or other relays) that the relay follows — with each one's account count, latest seq, and status.

com.atproto.sync.getHostStatus

gets the status of one upstream host.

com.atproto.sync.listRepos

lists the repositories the relay knows about — each one's DID, latest revision, and latest commit CID.

com.atproto.sync.getRepoStatus

gets the hosting status of one repository.

com.atproto.sync.requestCrawl

asks the relay to start following a host. (See “Getting a PDS Into a Relay”, below.)

Trust

Should you trust what comes out of a relay? The specification says: not completely.

Repository data is self-certifying. Each #commit carries a commit signed by the account's key. So, an application can check it by itself — without trusting the relay, and without asking the PDS.

Identity and account information (#identity and #account events) is not self-certifying. An application should check it itself — for example, by resolving the DID and handle itself. (See: How-To Resolve a Handle to a DID.)

The specification says:

Intermediary services (like public relays) may do some checks to reduce network abuse, but ultimately consuming services are responsible for validating message structure and verifying authenticity.

Also, a relay is allowed to change some events as they pass through. For example, it may replace the handle in an #identity event with the result of its own resolution, or remove it. And, it may filter out #identity events when the identity has not actually changed.

(One thing a relay should not do is check records against their Lexicons. The specification says relays “should not validate records against lexicons.”)

Relays and Spaces

Relays are for public data.

There is a proposal to add permissioned (private) data to ATProto, called spaces. With spaces, there are no relays — applications pull data directly from each user's repo host. (See: ATProto Syncer.)

But, even an application that only uses spaces still needs a firehose (such as a relay's), to find out about #account and #identity changes.

Running a Relay

If you want to run your own relay, Bluesky's reference implementation is the relay command in the indigo repository (written in Go).

Summary

An ATProto relay:

  1. follows the firehoses of many PDSes,
  2. combines them into a single firehose (com.atproto.sync.subscribeRepos) — a WebSocket of CBOR events (#commit, #sync, #identity, #account),
  3. is an optimization — so applications do not each need to connect to every PDS,
  4. is not where users' data lives, and
  5. does not need to be trusted for repository data — but applications should check identity and account information themselves.
