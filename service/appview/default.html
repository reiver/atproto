ATProto AppView

the service that turns the network's data into an application

by Charles Iliya Krempeaux

An AppView is a type of AT-Protocol (ATProto) service that collects data from across the network, and turns it into what an application shows its users — timelines, threads, profiles, like counts, search results, etc.

The ATProto glossary puts it this way:

An AppView is an application in the Atmosphere. It's called an "AppView" because it's just one view of the network. The canonical data lives in data repos which is hosted by PDSes, and that data can be viewed many different ways.

An AppView is not where users' data lives. The data lives on each user's Personal Data Server (PDS). An AppView is an index built from that data — one particular view of it.

In other words, an AppView is the back-end of an application. For example, Bluesky's AppView is the back-end of the Bluesky application. And, other applications (that use different kinds of records) have their own AppViews.

The glossary compares AppViews to search engines:

AppViews function a bit like search engines on the Web: they aggregate data from across the Atmosphere to produce their UIs.

Where an AppView Fits

Here is how data flows from a user, through the network, to an AppView, and back out to other users:

  1. a user writes a record (such as a post) to their PDS,
  2. the PDS announces the change on its firehose,
  3. a relay combines that firehose with the firehoses of many other PDSes,
  4. the AppView reads the relay's firehose, and updates its index, and
  5. applications ask the AppView for timelines, profiles, threads, etc.

The glossary says: “AppViews use a Relay to fetch user data.” (Although, a small AppView could read PDS firehoses directly, without a relay.)

Note that writes do not go to the AppView. They go to the user's PDS. The AppView only finds out about them later, from the firehose. (The glossary says AppViews “also communicate with users' PDSes to publish information on their repos” — that is, an application writes to a user's PDS on the user's behalf, after the user logs in with OAuth.)

The ATProto overview describes the 3 core services like this:

The three core services in our network are Personal Data Servers (PDS), Relays, and App Views.

What an AppView Adds

If the data lives on the PDS, why do we need an AppView at all?

Because a PDS only knows about its own users' records. Lots of things an application needs can only be computed by looking at everyone's records.

An AppView also does hydration — when it returns a post, it fills in things such as the author's handle and avatar, the like count, the reply count, and any moderation labels. That way, the application gets everything it needs to show the post in a single response.

More Than One AppView

Since an AppView is “just one view of the network”, there can be more than one AppView for the same kind of data.

For example, at the time of writing, both of these answer the Bluesky API (app.bsky.*):

How Applications Reach an AppView

There are 2 ways an application can talk to an AppView:

Directly

An AppView can offer public XRPC API end-points that do not require logging in. For example, the getProfile request above went directly to public.api.bsky.app, with no login.

Through the User's PDS (Service Proxying)

When a user is logged in, an application usually sends its requests to the user's PDS, and the PDS forwards them to the AppView. The specification calls this service proxying:

The PDS acts as a generic proxy between clients and other atproto services. Clients can use an HTTP header to specify which service in the network they want the request forwarded to (eg, a specific AppView or Labeler service). The PDS will do some safety checks, then forward the request on with an inter-service authentication token (JWT, described above) issued and signed by the user's identity.

The PDS then forwards the request to the serviceEndpoint, adding a short-lived JWT, signed with the user's key. The JWT tells the AppView which user the request is for:

iss

the user's DID.

aud

the AppView's DID (and service identifier). The AppView must check that this is itself.

lxm

the XRPC API end-point the token is for (such as app.bsky.feed.getTimeline).

exp

when it expires. (The specification says 60 seconds is a good lifetime.)

The AppView checks the JWT's signature against the key in the user's DID document. That way, the AppView can give personalized answers — such as the user's own timeline — without the user ever logging in to the AppView itself.

This is also how a user (or their application) can choose an AppView — by changing the atproto-proxy header.

AppViews and Moderation

An AppView is where moderation labels are usually applied to what users see. The label specification says:

Labels are often "hydrated" in to HTTP API responses by atproto services, such as AppViews.

An application chooses which labelers it wants labels from with the atproto-accept-labelers HTTP header. The AppView says which ones it applied with the atproto-content-labelers header. (A PDS passes these headers through when proxying.)

In the atproto-accept-labelers header, a labeler can also be marked with the redact parameter. Then, for content with the special !takedown or !suspend labels, the AppView removes the content from its response entirely, rather than just labeling it.

This fits ATProto's idea that speech and reach are separate layers. A user's PDS hosts what they say (speech). An AppView decides what to show, and to whom (reach).

AppViews and Spaces

Everything above is about public data.

There is a proposal to add permissioned (private) data to ATProto, called spaces. For spaces, there is no relay and no firehose. Instead, an AppView that wants to show the data in a space pulls it directly from each user's repo host — which makes the AppView a syncer.

Summary

An ATProto AppView:

  1. is the back-end of an application,
  2. reads the network's data (usually from a relay's firehose), and builds an index from it,
  3. computes things no single PDS can — such as follower counts, like counts, feeds, and search,
  4. is not where users' data lives, and does not receive writes,
  5. is reached directly, or through the user's PDS with the atproto-proxy header, and
  6. is “just one view of the network” — there can be more than one, and they can give different answers.
