ATProto Syncer

the service that keeps its own copy of a permissioned “space” up-to-date

by Charles Iliya Krempeaux

A syncer is a type of AT-Protocol (ATProto) service that keeps its own copy of a space in sync, by pulling data from the servers that host it.

The proposal that defines it puts it this way:

Syncer: an application that keeps its own copy of a space in sync by pulling from repo hosts.

Notice the word “application”. A syncer is not a separate service that applications use — the way an application might use a relay. A syncer is the application. (Or, more precisely, the back-end part of the application.)

Compare how an application gets public data with how it gets data from a space:

With spaces, there is no relay (or any other service) in the middle. The application pulls the data directly from each user's PDS, and keeps its own copy. Pulling the data, and keeping that copy up-to-date, is what makes the application a syncer.

So, for example, if you are building a private-forum application, then your application's back-end is the syncer. It pulls the forum's data, stores it in its own database, and serves it to your users however you choose. The proposal does not define any XRPC API end-points for reading data from a syncer. (The only end-points a syncer implements are for receiving notifications — see step 4, below.)

To understand what a syncer is, you first need to understand what a space is. And, why spaces need something like a syncer at all.

Note! At the time of writing, spaces and syncers are a proposal — proposal 0016, “Atproto Spaces”. They are not (yet) part of the ATProto specification. The proposal itself says:

This is a proposal, not the final specification. Details, terminology, and behaviors are all likely to change.

This article describes the proposal as of November 2026.

Public Data versus Permissioned Data

Most of ATProto is about public data. (The proposal calls this public broadcast.)

With public data:

  • each user has a repository on their Personal Data Server (PDS),
  • the records in that repository (posts, likes, follows, etc) can be read by anyone,
  • relays collect changes from many PDSes into a single stream (the “firehose”), and
  • applications read the firehose to build their views.

But, not all data should be public. The proposal lists some examples of data that should not be:

  • personal data — bookmarks, mutes, drafts,
  • gated content — paid newsletters, subscriber-only posts,
  • socially shared — private posts, stories,
  • groups — private forums, communities, group chats.

The proposal calls this permissioned data. And, the proposal adds a new part to ATProto for it — called ATProto spaces.

(Note that spaces are about access control, not secrecy. They are not end-to-end encrypted. The servers that handle the data can read it.)

Spaces

A space is a group of records that only some people (and some applications) are allowed to read. For example: a private forum.

A space is identified by 3 things:

space authority

a DID — the owner of the space, who decides who may read it.

space type

an NSID — what kind of space it is (such as com.atmoboards.forum).

space key (skey)

a string — to tell apart different spaces of the same type, with the same owner.

These 3 are put together into an at:// URI, with the word space in it:

Here is the important part — the records in a space are not all stored in one place.

Each user stores their own records for a space on their own PDS. (The proposal calls one user's records in one space a space repo.) So, if Alice, Bob, and Carol all post in the same private forum, then the forum's data is spread across 3 (possibly different) servers:

And, unlike with public data, there are no relays and no firehose for spaces.

So, how does an application show you the whole forum? It has to go to each of those servers, and pull the data itself. That is what a syncer does.

The Services Involved

There are 3 roles that a syncer deals with:

repo host

stores and serves users' space repos. (Usually the user's PDS.)

space host

answers for a space as a whole — it hands out permission to read the space, keeps the list of who has written to the space, and sends out notifications when something changes. (Usually the space authority's PDS.)

(For more on space hosts, see: ATProto Space Host.)

syncer

keeps its own copy of the space, by pulling from the repo hosts.

Notice that the space host does not hand out the records themselves. It only knows who has records, and when they changed. The records themselves always come from the repo hosts.

Who would run a syncer? Any application that needs to show (or process) the data in a space — for example, an AppView for a private forum. The proposal also says that a moderation service “must hold a space credential like any other syncer”.

An application that serves many users only needs to pull each space repo once. It then serves its users from its own copy.

(If an application is made of several services that all need the data, one syncer can keep the copy and serve it to the others — see: ATProto Space Mirror.)

What a Syncer Does

Here is the life of a syncer, step-by-step.

Step 1: Get a Space Credential

A syncer cannot just read a space. It needs permission. That permission is a token called a space credential.

To get a space credential, the syncer calls com.atproto.space.authorizeSpaceSync on the space host. (To find the space host, resolve the space authority's DID to its PDS — see: How-To Resolve a DID to a PDS.)

The request looks like this:

credentialKey

(required) a public-key that the syncer just made (a P-256 key, written as a did:key). The space credential gets tied to this key, so that only the syncer can use it.

delegationToken

(if the space requires it) proof that a user who is allowed to read the space has authorized this application. The syncer gets it from that user's PDS, using com.atproto.space.getDelegationToken. (This requires the user to have given the application permission through OAuth.)

clientAttestation

(if the space requires it) proof of which application is asking.

notify

(optional) where to send notifications when the space changes. (See step 4.)

If the space authority says yes, the response contains the space credential, plus the space's current revision.

A space credential is short-lived — 10 minutes by default (and at most 60 minutes). So, a syncer calls authorizeSpaceSync again, before its space credential expires. (This is also how access gets taken away — if the space authority stops saying yes, the syncer's space credential soon expires.)

When the syncer uses the space credential, it sends it in the Authorization header, along with an HTTP Message Signature made with the key from credentialKey:

One space credential works with every repo host in the space. The Atproto-Space-Audience header says which user's space repo the request is for.

Step 2: Find Out Who Has Written to the Space

Since the records in a space are spread across many servers, a syncer first needs to know whose space repos to pull.

For this, the syncer calls com.atproto.space.listWriters on the space host. It returns the writer set — the list of accounts that have written at least one record to the space. For each account, it also returns that space repo's current revision (repoRev) and digest (data).

Two things to note:

  • The writer set is not a member list. It only lists accounts that have written something. (People who only read are never listed.)
  • The writer set is only a starting point. The repo host is the source of truth for what is actually in each space repo.

A syncer does not treat a space repo that is not in the writer set as part of the space.

Step 3: Pull Each Space Repo

Next, for each account in the writer set, the syncer pulls that account's space repo from its repo host. (To find the repo host, resolve the account's DID to its PDS.)

There are 2 ways to do this:

the whole thing — com.atproto.space.getRepo

downloads the whole space repo, as a single file (a STAR archive). This is used the first time, or whenever the syncer's copy cannot be fixed any other way. (The proposal calls this full-state recovery.)

just the changes — com.atproto.space.listRepoOps

returns the list of changes (creates, updates, deletes) since a given revision. This is the normal way to stay up-to-date. (The proposal calls this incremental sync.)

How does a syncer know whether its copy is correct?

Each space repo has a commit. The commit includes a digest (data) computed from all the records in the space repo. The syncer computes the same digest over its own copy. If the 2 digests are the same, then the copy is exactly up-to-date. If they are different, then the copy is behind (or damaged), and the syncer falls back to downloading the whole thing.

(The digest is a special kind of hash called a set hash — specifically, LtHash. It does not depend on the order records were written in. And, a record can be added or removed from it without re-hashing everything. So, the syncer can keep it up-to-date as it applies each change.)

Because the correctness check is done with the digest, the proposal calls the sync self-healing — if a syncer misses a change, the next sync will notice.

A syncer also needs to fetch any BLOBs (images, videos, etc) that the records refer to. It uses com.atproto.space.listBlobs and com.atproto.space.getBlob for that.

Step 4: Get Notified of Changes

A syncer could keep checking every space repo over and over again (polling). But, that is wasteful. So, instead, a syncer can ask to be notified when something changes.

To do this, the syncer includes the notify object when it calls authorizeSpaceSync (step 1):

endpoint

the base HTTPS URL of the syncer.

token

a secret, made up by the syncer. (For example, 32 random bytes, base64 encoded.) The syncer should use a different token for each space.

This means a syncer is not only a client — it is also a server. It must implement these 2 XRPC API end-points, which the space host calls:

com.atproto.space.confirmRegistration

called once, before registering. The syncer checks that the token is one it made for that space, and echoes back the challenge it was sent.

com.atproto.space.notifySpaceUpdate

called whenever something changes — a space repo got a new revision, an account was removed from the writer set, the space was deleted, or the syncer's registration has expired.

Notice that the notification does not contain any records. It only says “this space repo has changed”. The syncer then goes to the repo host to get the change.

Notifications can be missed. Each notification includes the space's current and previous revision, so a syncer can notice a gap. When it does, (or after the syncer has been down for a while), it calls listWriters with a since revision, to find out what it missed. (If it has been more than 72 hours, the syncer should re-list the whole writer set instead.)

Step 5: Check That the Data Is Real

With public data, records are signed. So, anyone can prove who wrote them.

With spaces, that would be a problem. If private data leaked, the signatures would prove it was real. So, space repos do not use signatures.

Instead, the syncer and the repo host agree on a temporary shared secret, and the repo host uses it to compute a MAC (Message Authentication Code) over the commit or record. The syncer checks the MAC with the same secret.

This convinces the syncer that the data is real. But, since the syncer knows the secret too, it could have made the MAC itself — so the MAC proves nothing to anyone else.

How it works, briefly:

  • each account with space repos has an extra key in its DID document, with the id DID#atproto_kem,
  • for each request, the syncer makes a new temporary key, and combines it with the #atproto_kem key to get the shared secret (using HPKE, RFC 9180),
  • the syncer sends its temporary public-key in an Accept-Signature header,
  • the repo host answers with an Atproto-Space-Commit (or Atproto-Space-Record) header, and an hmac-sha256 HTTP Message Signature over it.

A Syncer's Responsibilities

Pulling the data is only part of the job. A syncer also has responsibilities:

deleting data when a space is deleted

When a space is deleted, the space host notifies every registered syncer. The syncer then calls authorizeSpaceSync again. If it gets back a SpaceDeleted error, the syncer should delete every copy of the space's data it has — including anything it computed from it.

deciding which of its users can see what

A space credential lets an application sync a space. It does not tell the application which of its users should be shown that space. The application has to figure that out (for example, from a published member list), and enforce it.

respecting account status

Data from deactivated or deleted accounts should not be shown. The space sync does not tell a syncer about account status changes. So, even a syncer that only syncs spaces still needs to subscribe to a firehose (com.atproto.sync.subscribeRepos), to get #account and #identity events.

Summary

A ATProto syncer:

  1. gets a short-lived space credential from the space host (and keeps renewing it),
  2. gets the writer set from the space host,
  3. pulls each space repo from its repo host — the whole thing at first, and then just the changes,
  4. checks its copy against each commit's digest, and checks each MAC,
  5. receives notifications from the space host, and pulls again when something changes, and
  6. deletes its copy if the space is deleted.

Again, this is all a proposal. Details are likely to change.
