ATProto XRPC-URI

xrpc:// and xrpc-unencrypted:// — one URI for an XRPC end-point

by Charles Iliya Krempeaux

An XRPC-URI is a URI that names an XRPC end-point on a server. It looks like this:

And, it gets turned into (“resolved” to) the regular HTTP or WebSocket URL that you actually connect to:

The XRPC-URI is not part of the ATProto specifications. It was created by the author of this article (Charles Iliya Krempeaux), and is implemented in the Go package github.com/reiver/go-xrpcuri. ATProto servers do not know about it, and do not need to — it is resolved by the client, before any request is made.

The package's README says:

The XRPC-URI is not part of the https://atproto.com/specs/xrpc specification, but is instead something invented by this package.

Two Schemes

There are 2 URI schemes:

xrpc

encrypted — resolves to https:// or wss://. This is the one to use almost always.

xrpc-unencrypted

unencrypted — resolves to http:// or ws://. For local development and testing — for example, xrpc-unencrypted://localhost:2583/com.atproto.server.describeServer.

The long, awkward name of xrpc-unencrypted is on purpose. Encrypted is the default, and gets the short name. Unencrypted has to be asked for by name. (The ATProto XRPC specification requires HTTPS outside of local development, anyway.)

The Parts of an XRPC-URI

So, there are 2 differences:

  1. the scheme is xrpc (rather than https), and
  2. there is no /xrpc/ in the path — the path is just the NSID.

The /xrpc/ can be left out because it is always there. The XRPC specification says “Paths must always be top-level, not below a prefix.” So, for an XRPC end-point, /xrpc/ carries no information. With it gone, the path of an XRPC-URI is exactly the NSID — the name of the end-point's lexicon.

Resolving an XRPC-URI

An XRPC-URI on its own does not say whether to use HTTP or WebSockets. That depends on the type of the XRPC request — which comes from the end-point's lexicon:

  • a query (HTTP GET),
  • a procedure (HTTP POST), or
  • a subscription (WebSocket).

So, resolving takes 2 inputs: the XRPC-URI, and the request type. The rules:

scheme query procedure subscription
xrpc https https wss
xrpc-unencrypted http http ws

And, /xrpc/ is put back in front of the NSID. For example:

XRPC-URI request type resolves to
xrpc://public.api.bsky.app/app.bsky.actor.getProfile?actor=bsky.app query https://public.api.bsky.app/xrpc/app.bsky.actor.getProfile?actor=bsky.app
xrpc://example.com/com.example.createThing procedure https://example.com/xrpc/com.example.createThing
xrpc://bsky.network/com.atproto.sync.subscribeRepos subscription wss://bsky.network/xrpc/com.atproto.sync.subscribeRepos
xrpc-unencrypted://localhost:2583/com.atproto.server.describeServer query http://localhost:2583/xrpc/com.atproto.server.describeServer

(The firehose example is from the ATProto Relay article. Notice that the XRPC-URI for the firehose looks just like the one for any other end-point. Only the request type is different.)

The package's README compares this to how most developers do not think about how an HTTP URI becomes a TCP connection:

MOST DEVELOPERS WHO ARE JUST MAKING XRPC CLIENT REQUESTS DO NOT HAVE TO WORRY ABOUT THE DETAILS OF THE RESOLUTION. IN THE SAME WAY THAT MOST DEVELOPERS DO NOT HAVE TO WORRY ABOUT HOW HTTP URIS ARE RESOLVED TO TCP.

“Execute” and “Procedure”

The Go package also accepts execute as another name for procedure. A code comment explains why — so that all the request types can be verbs: execute, query, subscribe.

Rules

Here are the rules, as implemented by go-xrpcuri. (There is no separate written specification — the package is the reference.)

The scheme is case-insensitive.

XRPC://… works the same as xrpc://…. (This is the same as every URI scheme, per RFC 3986.)

The server (the “authority”) is required.

xrpc:///com.example.fooBar is an error — “has an empty 'authority'”. A port number is allowed — localhost:2583. The server name is normalized to lower-case.

No user-name or password.

An @ in the authority is not allowed. So, xrpc://alice@example.com/… is an error. (Logging in is done with HTTP headers — not in the URI.)

The path must be an NSID.

xrpc://example.com/not-an-nsid is an error. The NSID is normalized the NSID way — the domain part is lower-cased, but the name part keeps its case. So, APP.BSKY.actor.getProfile becomes app.bsky.actor.getProfile (and not app.bsky.actor.getprofile).

The query string is passed through.

Everything after the ? is carried over to the resolved URL. It follows the usual XRPC rules for query parameters.

Regular URLs are left alone.

If you give xrpcuri.Resolve() an https://, http://, wss://, or ws:// URL, it returns it unchanged. So, code that takes an XRPC-URI also accepts a plain URL.

XRPC-URIs and AT-URIs

ATProto already has a URI scheme — at://. They name different things:

at:// xrpc://
names data — a repository, a collection, or a record an end-point on a server
authority an account — a DID or a handle a server — a host name (and port)
path collection NSID + record key end-point NSID
example at://bsky.app/app.bsky.feed.post/3n2opitxdyc2j xrpc://public.api.bsky.app/app.bsky.feed.getPosts
defined by the ATProto specifications go-xrpcuri
registered with IANA yes (provisional) no

An at:// URI does not say which server to ask. (To find out, you resolve the account's DID to its PDS.) An xrpc:// URI always does.

Implementations

  • github.com/reiver/go-xrpcuri (Go) — parsing, normalizing, validating, joining, and resolving XRPC-URIs.
  • github.com/reiver/go-xrpc (Go) — an XRPC client (and server) that takes XRPC-URIs. For example, xrpc.Query(&response, "xrpc://public.api.bsky.app/app.bsky.actor.getProfile?actor=reiver.bsky.social"). (XRPC-URIs first appeared here, in August 2024, and were moved into go-xrpcuri in 2025.)

Since resolving is simple, it is easy to implement in other programming languages: check and remove the scheme, lower-case the server name, check the NSID, and then put together https:// (or wss://, http://, ws://) + server + /xrpc/ + NSID + query.

Summary

An XRPC-URI:

  1. names an XRPC end-point on a server — xrpc://server/NSID?parameters,
  2. is not part of the ATProto specifications — it comes from go-xrpcuri,
  3. has 2 schemes — xrpc (encrypted) and xrpc-unencrypted (for local development),
  4. leaves out /xrpc/, since every XRPC path has it,
  5. is resolved by the client — to https / http for queries and procedures, and wss / ws for subscriptions, and
  6. is different from an at:// URI, which names data rather than an end-point.
