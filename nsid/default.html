ATProto Namespaced Identifier (NSID)

the names of record types, API end-points, and schemas

by Charles Iliya Krempeaux

There is an old joke in software engineering circles, whose origin seems to go back to Phil Karlton:

There are only two hard things in Computer Science: cache invalidation and naming things.

Leon Bambrick later popularized (and maybe even created) a modified version of this joke:

There are 2 hard problems in computer science: cache invalidation, naming things, and off-by-1 errors.

This joke took on a life of its own, with others creating their own version of the joke. (I even created a version of the joke.)

AT-Protocol (ATProto) tries to deal with the naming things problem with what it calls a Namespaced Identifier (NSID). Most of the time, you will hear and see a Namespaced Identifier referred to by its abbreviation: NSID.

I.e., an NSID is a type of name that is used by AT-Protocol (ATProto). And, in particular, NSID is a type of name that is used by AT-Protocol (ATProto) for naming:

  • XPRC API end-points — example: com.atproto.sync.getRecord
  • record types — example: app.bsky.feed.post
  • schemas
  • and more

AT-Protocol (ATProto) groups these things together and collectively calls them: lexicons. So, NSID is a type of name that is used by AT-Protocol (ATProto) for naming lexicons.

NSIDs look like these:

The specification says:

The basic structure and semantics of an NSID are a fully-qualified hostname in reverse domain-name order, followed by an additional name segment. The hostname part is the domain authority, and the final segment is the name.

An NSID is a name, not an address — you cannot just fetch it. It looks like a domain name written backwards, because it is one (plus a name on the end). The domain says who controls the name.

(If you have used Java packages, or Android app IDs, the reverse-domain style will look familiar.)

The Two Parts

Every NSID has 2 parts — split at the last dot:

domain authority

a domain name, written in reverse order — com.atproto.sync means the domain sync.atproto.com. Whoever controls that domain controls the NSID.

name

the name of the specific thing — written in camel-case, like getRecord, post, or fooBar.

Notice that the domain authority is the whole reversed domain — including any “sub-domains”. The specification points out:

It is common to use "subdomains" as part of the "domain authority" to organize related NSIDs. For example, the NSID com.atproto.sync.getRecord uses the sync segment. Note that this requires control of the full domain sync.atproto.com, in addition to the domain atproto.com.

Where NSIDs Are Used

NSIDs show up all over ATProto. In each case, the NSID is the name of a lexicon (a schema) that says what the thing is.

NSIDs also show up in the tokens services use to call each other — the lxm field of an inter-service JWT holds the NSID of the end-point it may be used for. (See: ATProto AppView.)

References Inside Lexicons

A lexicon can refer to a definition in another lexicon, with an NSID plus a # fragment. For example, com.atproto.label.defs#selfLabels is the selfLabels definition in the com.atproto.label.defs lexicon. (The fragment is not part of the NSID.)

Spaces

In the proposal for spaces, a space type is an NSID (for example, com.atmoboards.forum), and so is each policy type (for example, com.atproto.memberspace.policy).

Permissions

OAuth permissions name record types and end-points by NSID too — for example, repo:app.bsky.feed.post — or * for all of them. (Partial wildcards are not supported there.) And, permission sets are themselves lexicons, named by NSID.

Who Controls an NSID

Since the domain authority is a domain name, whoever controls the domain controls every NSID under it. For example:

  • app.bsky.* — Bluesky, who controls bsky.app.
  • com.atproto.* — the protocol itself (atproto.com).
  • community.lexicon.* — whoever controls lexicon.community.

So, to make your own record types or end-points, use a domain you control. If you own example.com, your NSIDs start with com.example..

The specification also says “having multiple NSIDs that differ only by casing is not allowed. Namespace authorities are responsible for preventing duplication and confusion.”

Controlling the domain is also how a lexicon is found. To resolve an NSID to its lexicon, you drop the name, reverse the rest, and look up a DNS TXT record — for app.bsky.feed.post, that is _lexicon.feed.bsky.app. (For the details, see: How-To Resolve a Lexicon.)

Syntax Rules

Here are the rules, from the specification:

the whole NSID
  • only ASCII characters,
  • segments separated by periods (.),
  • at least 3 segments, and
  • at most 317 characters.
the domain authority
  • at least 2 segments,
  • at most 253 characters, including periods (but see the note below),
  • each segment is 1 to 63 characters,
  • only letters (a-z, A-Z), digits (0-9), and hyphens (-),
  • segments cannot start or end with a hyphen,
  • the first segment (the top-level domain) cannot start with a digit, and
  • not case-sensitive — it should be normalized to lowercase.
the name
  • 1 to 63 characters,
  • only letters and digits — no hyphens,
  • cannot start with a digit, and
  • is case-sensitive — it should not be normalized.

A Note About the 253 Character Limit

The specification says the domain authority can be at most 253 characters. (That is the usual limit for a domain name — and 253 + 1 + 63 = 317, the overall limit.)

But, Bluesky's own interoperability test vectors list this as valid:

Its domain authority is 283 characters (and the whole thing is 287). And, Bluesky's TypeScript and Go implementations only check the 317 character total. So, in practice, implementations accept a domain authority longer than 253 characters — as long as the whole NSID is at most 317.

Best Practices

  • The specification “strongly” encourages domain authorities made of only letters — no digits or hyphens — since that “makes it significantly easier to generate client libraries in most programming languages.”
  • NSIDs are case-sensitive for display, storage, and validation. The specification says “Implementations should not force-lowercase NSIDs.”
  • For choosing names, see the Lexicon Style Guide.

Globs

To refer to a group of NSIDs, a trailing * can be used — for example, com.atproto.*. The specification says this “would refer to any NSIDs under the atproto.com domain authority, including nested sub-domains”. A * by itself matches every NSID.

The rules:

  • only one *,
  • it must be the last character, and
  • it must come right after a period (no partial matches — com.example.foo* is not allowed).

A glob is not itself an NSID. (The test vectors list com.example.foo.* as an invalid NSID.)

Summary

An ATProto Namespaced Identifier (NSID):

  1. names a lexicon — a record type, an XRPC end-point, etc,
  2. is a reversed domain name (the domain authority), plus a name — split at the last period,
  3. is controlled by whoever controls that domain,
  4. is used in at:// URIs, $type, /xrpc/ URLs, and more, and
  5. is at least 3 segments and at most 317 characters, with a case-insensitive domain authority and a case-sensitive name.
