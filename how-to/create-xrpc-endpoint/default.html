How-To Create an XRPC API End-Point

/xrpc/ com.example.math.add link.reiver.math.add

by Charles Iliya Krempeaux

ATProro does API calls over something it calls XRPC. But, despite ATProro being very much associated with social media, Bluesky, and the ATmosphere (Blacksky, rpg.actor, Tangled, etc) — XRPC has nothing to do with any of those things. XRPC is just a way of creating APIs.

For example, you could make an XRPC API end-point to add 2 integers. (For example: adding 7 + 8.) In fact, that example is a good way to learn and understand XRPC. So, let's do that.

This article goes over how-to create an AT-Protocol (ATProto) XRPC API end-point, from beginning to end, from a computer-programming point-of-view.

We will make an end-point that adds 2 numbers together. You send it 2 and 3. It sends back 5.

That is deliberately boring. There are no posts, no likes, no followers, and no timelines. That is the point:

There is nothing social-media about XRPC, and nothing Bluesky-specific about it. XRPC is just a way of doing RPC APIs over HTTP and JSON. ATProto happens to use it for its social features — but you can use it for anything.

What You Need, and What You Do Not Need

To make an XRPC end-point, you need:

  • an HTTP server, and
  • a JSON library.

That is it. (The example code in this article uses only the Go standard library.)

You do not need:

  • a Bluesky account,
  • an ATProto account,
  • a PDS (personal data server),
  • a DID or a handle,
  • a repository, a firehose, or a relay, or
  • an ATProto library.

(There is one exception. Publishing your Lexicon so that other people's software can find it does use an ATProto account. But, that is optional, and the end-point works without it. We will get to that at the end.)

Overview

Creating an XRPC end-point has 5 steps:

  1. choose a name for it — an NSID,
  2. decide if it is a query or a procedure,
  3. write a Lexicon — a schema that says what goes in, and what comes out,
  4. write the server, and
  5. call it.

After that, we will look at a problem with the name com.example.math.add, and switch to a domain that is real.

Step 1: Choose an NSID

Every XRPC end-point has a name. That name is an NSID (short for Namespaced Identifier).

We will start with this one: 


com.example.math.add

An NSID is an Internet domain written backwards, with a name on the end:

The authority is com.example.math. Written forwards, that is the Internet domain math.example.com. Notice that it is math.example.com — not example.com. Every segment except the last one is part of the domain.

The name is add.

The idea is that whoever controls the domain math.example.com gets to decide what com.example.math.add means. (That will matter later.)

A note on the name: the Lexicon Style Guide suggests “verb-noun” names for end-points — such as getPost, listLikes, or createRecord. add is just a verb. It is still a valid NSID, and it reads well, so we will keep it. But, for a real project, a name like addNumbers would follow the style guide more closely.

(The rules for the name: it can only use the ASCII letters A–Z and a–z, and the digits 0–9. It cannot start with a digit. And, it is case-sensitive — add and Add are different names.)

Step 2: Query or Procedure?

An XRPC end-point is one of 2 types:

query — HTTP GET

reads something. The inputs go in the URL's query string. The specification says queries “are cacheable and should not mutate resource state.”

procedure — HTTP POST

does something. The inputs usually go in a JSON request body. The specification says procedures “are not cacheable and may mutate state.”

We will make com.example.math.add a procedure.

(To be honest, adding 2 numbers does not change anything, and the answer could be cached. So, it could have been a query instead — GET /xrpc/com.example.math.add?a=2&b=3. That would also be fine. We are making it a procedure because a procedure shows more of how XRPC works — a request body, a response body, and the Content-Type header. Note that the specification says a procedure “may mutate state” — not that it must.)

Step 3: Write the Lexicon

A Lexicon is a schema, written in JSON. For an end-point, it says what the request looks like, and what the response looks like. It is the contract between the server and its clients.

Let's go through it, piece by piece:

"lexicon": 1

the version of the Lexicon language. It is always 1 (for now).

"id": "com.example.math.add"

the NSID from step 1.

"defs" and "main"

a Lexicon file can hold more than one definition. The one named main is the end-point itself.

"type": "procedure"

the choice from step 2. (For a query, this would be "query".)

"input"

what the request body looks like: JSON, with 2 required fields, a and b, that are both integers.

"output"

what the response body looks like: JSON, with 1 field, sum, that is an integer.

So, a request body looks like this: 


{"a":2,"b":3}

And, a response body looks like this: 


{"sum":5}

By convention, Lexicon files are stored in a directory tree that follows the NSID. So, this one would be saved as: 


lexicons/com/example/math/add.json

Only Integers — No Decimals

You might have noticed that a and b are integers — not just “numbers”. That is not a choice we made. It is a rule.

Lexicon does not have a floating-point type. There is no float, no double, no decimal, and no number. The ATProto data model specification says floats are “not allowed in atproto”.

So, our end-point can add 2 and 3. But, it cannot add 2.5 and 3.

(Why? The same data model is used for records stored in ATProto repositories, where data is identified by its hash. Floating-point numbers do not always encode back to the exact same bytes after being decoded, which would change the hash. If you really need decimals, the specification suggests sending them as strings — for example, "2.5".)

Why the Minimum and Maximum?

The minimum and maximum limit a and b to between negative 1 quadrillion and positive 1 quadrillion: 


-1000000000000000  to  1000000000000000

Lexicon integers can be up to 64 bits. But, JavaScript can only handle integers up to 53 bits exactly — that is, up to 9007199254740991. After that, JavaScript silently rounds them. For this reason, the specification says integers “should be limited to 53 bits of precision.”

This is not just a theory. I ran the official JavaScript XRPC server library (@atproto/xrpc-server), with this same Lexicon but without the limits, and asked it to add 9007199254740993 and 0. It answered: 


{"sum":9007199254740992}

That is the wrong answer — and there was no error.

With the limits, the biggest possible sum is 2 quadrillion (2000000000000000). That is well under the 53-bit limit. So, the answer is always exact — in any programming-language.

Step 4: Write the Server

An XRPC end-point lives at /xrpc/, followed by its NSID:

(The specification says the path must be at the top-level. So, http://localhost:8080/api/xrpc/com.example.math.add would not be allowed.)

When a request comes in, our server will do 5 things, in order:

  1. check that the HTTP method is POST (because it is a procedure),
  2. check that the Content-Type is application/json,
  3. read the JSON request body,
  4. check the input against the Lexicon — both fields there, both integers, both within the limits, and
  5. add the 2 numbers, and send back the sum.

If any check fails, the server sends back an XRPC error. An XRPC error is JSON with 2 fields:

error

required — the name of the error, in UpperCamelCase, with no spaces (for example, InvalidRequest).

message

optional — a description of what went wrong, for humans.

For example: 


{"error":"InvalidRequest","message":"Content-Type must be application/json"}

A few things to note:

  • It is just net/http and encoding/json. No ATProto library. No Bluesky library.
  • The fields are *int64 (pointers), not int64. If a field is missing from the JSON, Go would otherwise just set it to 0 — and we could not tell the difference between {"a":2} and {"a":2,"b":0}.
  • Decoding into an int64 means Go rejects decimals (like 2.5) and strings (like "2") for us.
  • Extra fields (for example, {"a":2,"b":3,"c":9}) are ignored. That is on purpose. The Lexicon specification says unexpected fields “should be ignored”, so that a Lexicon can add new optional fields in the future without breaking old servers.
  • Using the wrong HTTP method returns 400 with InvalidRequest. That is what the official XRPC server library does too.

What About Other NSIDs?

The last handler, /xrpc/, catches requests for any other NSID — for example, com.example.math.subtract, which we did not make. It returns 501 with the error name MethodNotImplemented.

Why 501, and not 404?

  • The official XRPC server library (@atproto/xrpc-server) returns 501 MethodNotImplemented for an NSID it does not have.
  • The official XRPC client library (@atproto/xrpc) treats a 404 as “XRPC Not Supported” — meaning that the server does not do XRPC at all.

So, 501 tells a client the most accurate thing: “this server does XRPC, but not that end-point.”

(The specification itself is a bit vague here. It says 404 can mean the server “does not support this endpoint”, and 501 means the end-point “is known, but not implemented”. And, in practice, servers vary — when I asked Bluesky's public API server for com.example.math.add, it returned 405. So, if you write a client, be ready for any of these.)

Does the Server Read the Lexicon File?

No. Our server does not read add.json. Instead, the checks in the code follow the Lexicon by hand — the 2 required fields, the integer type, and the same minimum and maximum.

That is fine for one small end-point. For bigger projects, there are tools that read Lexicon files and generate code for you — such as @atproto/lex-cli (for TypeScript), and lexgen in Bluesky's indigo repository (for Go). But, you do not need them.

Even when the server does not read it, the Lexicon is still useful. It is the documentation. It tells anyone who wants to call your end-point exactly what to send, and what they will get back.

The Problem with example.com

Everything works. But, there is a problem with the name com.example.math.add.

Remember, from step 1, that whoever controls the domain in an NSID gets to decide what it means. This is what keeps NSIDs from clashing. If you own a domain, nobody else can (legitimately) define end-points under it.

But, nobody owns example.com. It is reserved, for use in documentation — like this article. (See RFC 2606 and RFC 6761.) That means:

  • Anyone can use it. Someone else could make their own com.example.math.add that works differently from ours — maybe it returns {"result":5} instead of {"sum":5}. Neither of us would be “right”.
  • Nobody can publish its Lexicon. Software can look up a Lexicon from its NSID, using DNS. (That is covered in How-To Resolve a Lexicon.) But, only the owner of the domain can create that DNS record — and example.com has no owner.

You can see that there is no Lexicon published for it:

So, com.example is fine for learning, and for examples. But, for an end-point that other people will use, you should use a domain that you actually control.

Publishing the Lexicon (Optional)

With a real domain, you can publish your Lexicon, so that other people's software can find it from just the NSID.

This is the one part of this article that uses ATProto itself. Lexicons are published as records in an ATProto repository. So, you need an ATProto account. (Again, this is optional — your end-point works without it.)

Publishing has 2 steps:

  1. save the Lexicon as a record in your repository, and

Summary

To create an XRPC API end-point:

  1. Choose an NSID — a domain you control, written backwards, with a name on the end (link.reiver.math.add). Use com.example only for examples.
  2. Decide if it is a query (GET, reads) or a procedure (POST, does).
  3. Write a Lexicon that describes the input and the output. Remember: integers only (no decimals), and keep them within 53 bits.
  4. Write an HTTP handler at /xrpc/ plus the NSID, that checks the method, the Content-Type, and the input — and returns errors as {"error": …, "message": …}.
  5. Call it with any HTTP client — even curl.
  6. Optionally, publish the Lexicon — as a com.atproto.lexicon.schema record, plus a _lexicon. DNS TXT record.

And, none of it had anything to do with social media.
