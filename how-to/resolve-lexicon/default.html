How-To Resolve a Lexicon

_lexicon. com.atproto.lexicon.schema com.atproto.repo.getRecord

by Charles Iliya Krempeaux

This article goes over how-to resolve an AT-Protocol (ATProto) Lexicon from a computer-programming point-of-view.

For example, resolving the NSID: 


app.bsky.feed.post

To the Lexicon schema that describes what a Bluesky post looks like.

Lexicons and NSIDs

A Lexicon is a schema. It is written in JSON. It describes the shape of some data in ATProto — such as a type of record (a post, a like, a follow, a profile, etc), or an XRPC API end-point.

Every Lexicon has a name. That name is called a NSID (short for Namespaced Identifier). For example:

  • app.bsky.feed.post
  • app.bsky.actor.profile
  • com.atproto.repo.getRecord
  • com.atproto.identity.resolveHandle

An NSID looks like an Internet domain written backwards, with a name on the end:

The authority is the part that is an Internet domain (written backwards). The name is the last segment.

Resolving a Lexicon means: given an NSID, find and download its Lexicon schema. You might want to do this, for example, to validate a record whose type your software has never seen before.

Overview

Lexicons are published as records in an ATProto repository — the same kind of repository that holds a user's posts and likes. The owner of the Internet domain in the NSID says which repository, using DNS.

So, resolving a Lexicon has 4 steps:

  1. turn the NSID into a DNS name,
  2. look up the DNS TXT record to get a DID,
  3. resolve the DID to a PDS, and
  4. fetch the Lexicon record from the PDS.

If this looks familiar, it should. Steps 2 and 3 are very similar to resolving a handle to a DID, and resolving a DID to a PDS.

Let's look at each of these steps in more detail.

Step 1: Turn the NSID into a DNS Name

To turn an NSID into a DNS name:

  1. remove the name (the last segment),
  2. reverse the order of the segments that are left, and
  3. put _lexicon. in front.

A few rules:

  • The prefix is _lexicon. — not _atproto. (which is used for handles).
  • There is no HTTPS method for this. (Unlike handles, which can also use /.well-known/atproto-did.) It is DNS only.
  • Do not go up (or down) the DNS hierarchy looking for a record. If there is no record at _lexicon.feed.bsky.app, then do not try _lexicon.bsky.app. Resolution has simply failed.

(The specification does not say what to do if there are 2 or more did= records. A sensible choice is to do what is done for handles — ignore records that do not start with did=, and fail if there are records with different DIDs.)

Shortcut: Ask a Server To Do It

There is also an XRPC API end-point for resolving Lexicons:

com.atproto.lexicon.resolveLexicon

resolves an ATProto Lexicon (NSID) to a schema.

It takes one parameter, nsid. And, it returns the uri, the cid, and the schema.

However, at the time of writing, it is not widely available. For example, Bluesky's public API server (public.api.bsky.app) responded with MethodNotImplemented, and a PDS responded with AuthMissing (it required logging in). So, it is good to know how to do the resolving yourself.

Caching

The specification says that you should not cache the DNS result for a long time.

(The owner of an Internet domain can move their Lexicons to a different repository by changing the DNS record. And, unlike changes to the Lexicon records themselves, changes to DNS are not announced on the “firehose”.)

Summary

To resolve an ATProto Lexicon:

  1. Remove the name from the NSID, reverse the rest, and put _lexicon. in front — app.bsky.feed.post → _lexicon.feed.bsky.app.
  2. Look up the DNS TXT record for that name, and use the value after did=. (Do not try parent domains.)
  3. Resolve the DID to its PDS.
  4. On the PDS, call com.atproto.repo.getRecord with repo = the DID, collection = com.atproto.lexicon.schema, and rkey = the NSID.
  5. Check that the record's $type, lexicon, and id are what you expect.
