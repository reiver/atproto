How-To Resolve a Handle to a DID (decentralized identifier)

_atproto. /.well-known/atproto-did com.atproto.identity.resolveHandle

by Charles Iliya Krempeaux

This article goes over how-to resolve an AT-Protocol (ATProto) handle to a decentralized identifier (DID) from a computer-programming point-of-view.

For example, resolving the handle: 


bnewbold.net

Which is also sometimes written in at-prefixed notation as: 


@bnewbold.net

To the DID: 


did:plc:44ybard66vv44zksje25o7dz

This is often the first thing a computer-program needs to do when working with an ATProto user. Because, a person usually gives you a handle. But, almost everything else in ATProto is built on the DID.

Handles and DIDs

ATProto has two main ways of identifying users:

ATProto handles

For example: 


reiver.blacksky.team
DIDs

For example: 


did:plc:scewmn2pl3oz36mxme2b6czz

ATProto handles are human-friendly ways of identifying ATProto users. DIDs are machine-friendly ways of identifying ATProto users.

A handle can change. (A person might switch from joeblow.bsky.social to joeblow.com, for example.) A DID is meant to not change. That is why software stores and refers to users by their DID, and only shows the handle to humans.

ATProto handles are just Internet domains. And, that is the key to resolving them — since a handle is an Internet domain, it is the owner of that Internet domain who says what DID the handle belongs to.

Step 0: Normalize the Handle

Before resolving a handle, clean it up.

Handles are often written with an “@” in front of them — @bnewbold.net. That “@” is not part of the handle. Remove it.

Two Methods

There are 2 ways to resolve an ATProto handle to a DID:

  1. a DNS TXT record, and
  2. an HTTPS request to a /.well-known/ URL.

Any particular handle might use either one. So, your code needs to support both.

Let's look at each of these in more detail.

Method 1: DNS TXT Record

To resolve a handle using DNS, put _atproto. in front of the handle, and look up the TXT records for that name.

For example, for the handle bnewbold.net, look up the TXT records for: 


_atproto.bnewbold.net

You can try this yourself, from the command-line, with the dig program:

The value of the TXT record starts with did=. Everything after the did= is the DID:

A few rules:

  • TXT records that do not start with did= should be ignored.
  • If there are 2 (or more) did= records with different DIDs, then resolution has failed.
  • If there are no did= records, then this method has failed — and you should try the other method.

The specification says this DNS method is the one that is recommended for individuals who use their own Internet domain as their handle.

Method 2: HTTPS Well-Known URL

To resolve a handle using HTTPS, make an HTTPS GET request to this URL: 


https://HANDLE/.well-known/atproto-did

Where HANDLE is replaced with the handle.

For example, for the handle rude1.blacksky.team, the URL is: 


https://rude1.blacksky.team/.well-known/atproto-did

You can try this yourself, from the command-line, with the curl program:

The body of the HTTP response is just the DID. There is no did= prefix here. There is no JSON. Just the DID, as plain text.

A few rules:

  • It must be HTTPS (on the default port, 443). Plain HTTP is only for local development and testing.
  • The HTTP status code must be a success (2xx).
  • The Content-Type should be text/plain. But, you do not need to strictly check it.
  • Strip any whitespace from the beginning and end of the body before using it. (For example, a trailing new-line.)
  • Follow HTTP redirects (such as 301 and 302) — up to a reasonable number of them.

The specification says this HTTPS method is meant for large services that give out many handles — such as *.bsky.social and *.blacksky.team. (It is easier for them to answer an HTTPS request than to create a DNS record for every user.)

Using Both Methods Together

Since you do not know ahead of time which method a handle uses, you try both.

The simple way to do this is: try DNS first; and if that fails, try HTTPS.

The specification also says it is OK to try both at the same time (in parallel), and use whichever succeeds first.

What if both methods succeed, but give different DIDs? Then the specification says to prefer the DNS result. (Or, to treat the result as ambiguous, and try again later.)

Verify: Check the DID Points Back to the Handle

You now have a DID. But, you are not done yet!

Anyone who owns an Internet domain can create a _atproto. TXT record (or a /.well-known/atproto-did file) that points to any DID — including your DID. So, a handle pointing to a DID is only half of the story.

The other half is that the DID must point back to the handle.

To do this, you resolve the DID to its DID document. (For a did:plc, you can get the DID document from https://plc.directory/DID.)

Shortcut: Ask a Server To Do It

If you do not want to do the resolving yourself, you can ask an ATProto server to do it for you. There is an XRPC API end-point for this:

com.atproto.identity.resolveHandle

resolves an ATProto handle to a DID.

For example:

Most Personal Data Servers (PDSes) also support this end-point.

Two things to keep in mind:

  • You are trusting that server to give you the right answer.
  • The lexicon for this end-point says it “does not necessarily bi-directionally verify against the the DID document”. So, you may still need to do the verification step yourself.

Caching

Resolving a handle involves the network — and thus is relatively slow. So, the specification says it is a best-practice to cache the result, and re-resolve it every so often.

(The specification notes that DNS TTL values are probably too short to use as the cache lifetime for this.)

Summary

To resolve an ATProto handle to a DID:

  1. Normalize the handle — remove any “@” prefix, and convert it to lower-case.
  2. Look up the DNS TXT records for _atproto.HANDLE, and use the value after did=.
  3. If that fails, GET https://HANDLE/.well-known/atproto-did, and use the (whitespace trimmed) body.
  4. Resolve the DID to its DID document, and check that the first at:// entry in alsoKnownAs is the same handle.
